Enterprises today need a clear way to extend their authentication and authorization controls into the agentic layer, often requiring either broad service account permissions or custom-built auth integrations that add operational overhead. When an AI agent running on Amazon Bedrock AgentCore (a platform to build, connect, and optimize agents at scale, with any framework or model) needs to call the Snowflake-managed MCP server (which exposes Snowflake Cortex Agents as one of its tool types) through the Model Context Protocol (MCP), the first question enterprises must answer is: how does the agent authenticate? In this post, we walk through three Open Authorization (OAuth) configurations we tested on Amazon Bedrock AgentCore Identity, a capability of Amazon Bedrock AgentCore: Snowflake OAuth (per-user, no external Identity Provider, or IdP), three-legged OAuth with a third-party Identity Provider (corporate single sign-on, or SSO), and two-legged OAuth with a third-party Identity Provider (shared service user). Amazon Bedrock AgentCore Identity also supports an on-behalf-of (OBO) grant (TOKEN_EXCHANGE) that delivers per-user identity for unattended workloads without a consent prompt. We focus on the three configurations we tested end-to-end, flagging where OBO fits as we go. By the end, you will be able to identify which pattern suits your enterprise scenario.

Amazon Bedrock AgentCore Gateway, a capability of Amazon Bedrock AgentCore, connects AI agents to external tool providers through MCP server targets. It targets the Snowflake-managed MCP server, which surfaces Cortex Search and Cortex Analyst as MCP tools that an MCP-aware client can discover and invoke. Rather than acting as a wrapper, the Gateway aggregates the capabilities of its configured targets into a single unified catalog, which it presents to the agent as one tools/list response.

The core focus of this post is the outbound authentication for Amazon Bedrock AgentCore Gateway: how it obtains and presents OAuth tokens to the Snowflake-managed MCP server. Amazon Bedrock AgentCore Identity acts as the credential broker: the Gateway obtains a workload token by calling GetWorkloadAccessTokenForJWT (because the Gateway uses JSON Web Token (JWT) inbound authentication), then calls GetResourceOauth2Token against the configured provider. AgentCore Identity owns the token vault, the token refresh, and the user-to-token binding, and it fetches, caches, and refreshes tokens automatically.

Patterns 2 and 3 (external IdP) follow standard OAuth flows, so they can extend to other OAuth-protected MCP servers, but validate the token claims, scopes, and audience settings for your SaaS provider. Only Pattern 1 is Snowflake-specific, because it relies on Snowflake’s built-in OAuth authorization server. The Snowflake-specific elements are the OAUTH_AUTHORIZATION_SERVER issuer-lock parameter, the session:role: / session:scope: grammar, BLOCKED_ROLES_LIST, LOGIN_NAME / EMAIL_ADDRESS mapping, and QUERY_HISTORY attribution. If your SaaS exposes its own internal OAuth server, you configure outbound OAuth the same way as Snowflake OAuth.

The following sections examine each pattern in detail: the authentication flow, configuration steps, and trade-offs to help you select the right approach for your use case.

The Snowflake OAuth pattern uses a three-legged OAuth (3LO) flow to deliver per-user authentication without requiring an external identity provider. Each user authenticates to Snowflake with their own credentials, consents to a specific Snowflake role, and Amazon Bedrock AgentCore Identity caches that user’s access and refresh tokens. Every subsequent Snowflake call executes as that user, and QUERY_HISTORY records their real username. Note that per-role consent is not the default. The Snowflake-managed MCP server advertises session:role:all and falls back to DEFAULT_ROLE, so you set OAUTH_SCOPES_SUPPORTED (an account-, database-, or schema-level parameter set with ALTER) to narrow the role scope the server advertises, and restrict ALLOWED_ROLES_LIST on the integration to enforce which roles a user can consent to (PRE_AUTHORIZED_ROLES_LIST does the opposite: it lists roles that skip the consent step).

In a recent development, what makes this pattern appealing is its simplicity: no external identity provider is required. Snowflake acts as both the authorization server and the resource server, exposing its own built-in OAuth endpoints (/oauth/authorize and /oauth/token-request). Setup follows a specific order, because the callback URL does not exist until the credential provider is created. The administrator first creates the CustomOauth2 credential provider in Amazon Bedrock AgentCore Identity with placeholder client credentials and records the callbackUrl that AgentCore Identity returns. That callbackUrl is then registered as the redirect URI on a Snowflake security integration created with TYPE = OAUTH and OAUTH_CLIENT = CUSTOM. Finally, the administrator updates the credential provider with the real client ID and secret issued by Snowflake and configures the provider’s oauthDiscovery with explicit authorization server metadata: the issuer (the Snowflake account URL), the authorization endpoint (/oauth/authorize), and the token endpoint (/oauth/token-request).

According to recent reports, access tokens are short-lived. By default, they last 600 seconds (maximum 3600). When an access token expires, Amazon Bedrock AgentCore Identity automatically uses the refresh token to obtain a fresh access token, with no user interaction required. If the security integration is configured to prevent refreshing tokens, the user must re-authorize through the consent screen. Refresh-token lifetime is controlled by OAUTH_REFRESH_TOKEN_VALIDITY. The reference implementation sets it to 86400 seconds (1 day), and Snowflake allows up to 90 days. OAUTH_ISSUE_REFRESH_TOKENS (default TRUE) governs whether refresh tokens are issued at all.

Note: By default, Snowflake helps prevent the ACCOUNTADMIN, ORGADMIN, GLOBALORGADMIN, and SECURITYADMIN roles from being used with OAuth integrations. This is controlled by BLOCKED_ROLES_LIST for Snowflake OAuth (and EXTERNAL_OAUTH_BLOCKED_ROLES_LIST for External OAuth), applies to all three patterns, and covers the primary role only. With OAUTH_USE_SECONDARY_ROLES = IMPLICIT, secondary roles can still carry these privileged roles.

This pattern combines per-user authentication with corporate single sign-on. Consumers sign in through the external IdP, which enforces multi-factor authentication (MFA), conditional access, and session policies. The IdP-issued JWT is presented to Snowflake, which validates it through its External OAuth security integration (optionally issuer-locked to the MCP server’s schema, database, or account with OAUTH_AUTHORIZATION_SERVER). Snowflake verifies the issuer, audience, and signature through a JSON Web Key Set (JWKS). It then maps a configurable claim, set with EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM (sub for Okta, upn for Microsoft Entra ID), to a Snowflake user’s LOGIN_NAME or EMAIL_ADDRESS (with EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE), and runs the query as that user. The security integration parameter values are case-sensitive.

According to recent reports, the key difference from Pattern 1: the authorization server is your corporate IdP (such as Okta, Microsoft Entra ID), not Snowflake. Snowflake remains the resource server. Users authenticate with the same credentials and policies they use for every other corporate application. No separate Snowflake passwords are required.

It has been revealed that on the Amazon Bedrock AgentCore side, Amazon Bedrock AgentCore Identity provides built-in credential provider vendors for popular identity providers (for example, OktaOauth2 and MicrosoftOauth2). These vendors accept the client ID, client secret, and IdP endpoints through includedOauth2ProviderConfig, compared to the generic CustomOauth2 provider used in Pattern 1. The Snowflake-managed MCP server uses pre-registered OAuth clients, so you register each client ID and secret in advance, which is why the create, record callbackUrl, register, enhancement sequence is required.

Token lifetime governance: Unlike Pattern 1 where Snowflake controls token lifetimes, access token and refresh token lifetimes are governed by the IdP, and Amazon Bedrock AgentCore Identity handles the refresh transparently. If a refresh token was issued, the user re-authenticates only when it expires, based on the IdP’s session policy. Otherwise, the user re-authenticates when the access token expires.

It has been revealed that the two-legged OAuth pattern uses the OAuth 2.0 client_credentials grant. This is a machine-to-machine flow with no user interaction. Amazon Bedrock AgentCore Identity obtains a JWT from the IdP using the configured client ID and client secret, and Amazon Bedrock AgentCore Gateway presents it to Snowflake, which executes the requests under a shared service user, regardless of which end user initiated the query.

This pattern is the most operationally direct: no consent screens, no per-user token vaults, no browser redirects. The owners follow the same code path. Amazon Bedrock AgentCore Identity fetches and caches the client_credentials token automatically, and the Amazon Bedrock AgentCore Gateway presents it on every outbound call to the Snowflake-managed MCP server.

In a recent development, the key difference from Patterns 1 and 2: there is no per-user identity propagation. Snowflake’s QUERY_HISTORY records a single service user for queries. The trade-off is operational simplicity at the cost of per-user audit granularity. On the Amazon Bedrock AgentCore side, the credential provider uses the client_credentials grant type: either a built-in vendor (OktaOauth2, MicrosoftOauth2) or the generic CustomOauth2 provider. Configuration requires the IdP’s token endpoint, client ID, and client secret. Amazon Bedrock AgentCore Identity fetches a token from the IdP on the first tool call (when the Gateway calls GetResourceOauth2Token), caches it, and, because client_credentials problems no refresh token, requests a fresh one before expiry. No agent-level code changes are required.

Sources indicate that because the two-legged OAuth target needs no user consent, the Amazon Bedrock AgentCore Gateway connects to the Snowflake-managed MCP server at target-creation time and discovers tools through implicit sync during target creation. In the 3-legged OAuth patterns (Patterns 1 and 2), the Gateway target supports two creation methods: (1) an admin completes the authorization code flow so tools are discovered by implicit sync, or (2) the admin provides the tool schema upfront. Sources indicate that the three configurations in this post cover two grant types: authorization_code (Patterns 1 and 2) and client_credentials (Pattern 3). Amazon Bedrock AgentCore Identity also supports on-behalf-of (OBO) token exchange (TOKEN_EXCHANGE), which delivers per-user identity for unattended workloads without a consent prompt.

Sources indicate that OBO exchanges an inbound user token for a Snowflake-scoped token that preserves the real user’s identity, so QUERY_HISTORY attributes each query to the actual user, while keeping the unattended, machine-to-machine flow of Pattern 3 (no browser redirect, no consent screen). On the Snowflake side it uses the same TYPE = EXTERNAL_OAUTH integration as Patterns 2 and 3 (optionally issuer-locked with OAUTH_AUTHORIZATION_SERVER). On the AgentCore side it is configured on the OAuth credential provider through onBehalfOfTokenExchangeConfig (grant mode TOKEN_EXCHANGE for Okta/RFC 8693, or JWT_AUTHORIZATION_GRANT for Microsoft Entra). OBO uses the External OAuth path (Patterns 2 and 3).

OBO is generally available on Amazon Bedrock AgentCore Identity, but it was outside the scope of the three configurations we tested for this post.

In this post, we walked through three OAuth configurations for authenticating AI agents to Snowflake Cortex AI over MCP through Amazon Bedrock AgentCore Gateway. Snowflake OAuth offers the simplest path to per-user audit trails with no external IdP dependency. Two-legged OAuth with an external IdP serves machine-to-machine through a shared service user.
