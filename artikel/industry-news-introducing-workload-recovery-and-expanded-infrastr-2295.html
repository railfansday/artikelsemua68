Industry News: Introducing workload recovery and expanded infrastructure checks on Amazon SageMaker HyperPod

🌐 Source: Amazon • 📅 18 Nov 2026 • ⏱️ 16 min read (3249 words, 📚 Deep Dive)
💡 Key Takeaways

  • Recent findings suggest that in this post, we walk through the three newly introduced capabilities that catch these failures.
📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that large training jobs can fail even when every node looks healthy. A GPU with a subtle fault can pass its stress tests and still return wrong values. When a job stalls on an NCCL timeout, it keeps its GPUs, and Slurm still shows it as running. If a device plugin crashes on one node, the job fails with an error that never mentions the plugin. Teams usually find these problems only after the loss diverges or the job fails, and by then the compute is spent. Each of these failures lowers goodput, the share of your cluster’s time that goes to useful training. Today, we’re introducing workload recovery and infrastructure checks on Amazon SageMaker HyperPod that catch these failures sooner and raise the goodput of your training workloads.

According to recent reports, sageMaker HyperPod already handles nodes that report hardware faults. The health monitoring agent (HMA) watches each node for GPU errors, deep health checks test nodes during provisioning, and automatic node recovery reboots or replaces faulty hardware. These features look at one node’s hardware at a time. They can’t tell whether the GPUs train correctly, whether a job is still making progress, or whether the Kubernetes components a job depends on are working.

Recent findings suggest that in this post, we walk through the three newly introduced capabilities that catch these failures. For each one, we show how to set it up and what it reports when it finds a problem:.

The existing HyperPod resiliency features check a single node at a time. The health monitoring agent (HMA) watches each node for GPU errors such as Xid and NVLink faults, Elastic Fabric Adapter (EFA) errors, and kernel errors. The InstanceStress deep health check runs DCGM level 4 diagnostics and tests each instance’s GPUs, GPU memory, NVLink, and EFA devices. The InstanceConnectivity check runs NCCL tests across GPU instances, or NCCOM tests on AWS Trainium. Together, these confirm that each node’s hardware works. They don’t show whether the GPUs compute correctly, whether a job is still making progress, or whether the cluster’s Kubernetes components are healthy. Three kinds of failure get past them:.

Sources indicate that each capability covers a different point in a training run. MultiNodeTrainingValidation runs when instances are provisioned, or on demand, and confirms that their GPUs train correctly. Hung job detection runs alongside each Slurm job and catches a job that has stopped making progress. Runtime goodput is the share of that time in which the job makes forward progress. Program goodput is the share of the hardware’s peak performance that the job gets. It has been revealed that consider a pre-training job running on 32 ml.p5.48xlarge instances (256 NVIDIA H100 GPUs). If the job hangs at 1:00 AM and no one notices until 9:00 AM, it wastes 256 instance-hours or 2,048 GPU-hours. At the SageMaker HyperPod on-demand price of approximately $66 per instance-hour in US East (N. Virginia), the hang costs about $16,900. With a 15-minute hung job detection rule, HyperPod cancels the stalled job and Slurm requeues it. The hang costs about $530 instead, saving approximately $16,400.

Sources indicate that the MultiNodeTrainingValidation deep health check trains a fixed, known-good workload, first on each instance and then across instances. It catches GPUs that pass InstanceStress and InstanceConnectivity but produce NaN or infinite loss once they train together. If an instance fails, HyperPod labels it as failed and, with automatic node recovery turned on, reboots or replaces it. When the check runs during provisioning, this happens before your jobs can use the instance.

Sources indicate that keep in mind that MultiNodeTrainingValidation tests the hardware with a fixed reference workload. A pass means the instances trained that workload correctly. It doesn’t guarantee that your own job will converge. We recommend running it on upcoming capacity, on replacement instances, and before long pre-training runs.

According to recent reports, HMA watches the hardware on each node, but many failures that stop a training job happen in Kubernetes. A device plugin can crash-loop until its node stops offering GPUs to the scheduler, or a taint can evict a job’s pods. The job error rarely names the pod or node involved, so engineers piece together what happened from kubectl output, per-rank logs, and timestamps.

Sources indicate that the HyperPod Kubernetes Resource Monitoring Agent watches these resources from one place in the cluster. When something breaks, it tells you what changed and which nodes, pods, and jobs are affected. It reports through Kubernetes events and structured CloudWatch logs. The agent only reports. It doesn’t reboot nodes or restart jobs, because the cause might be in the workload. HMA and HyperPod node recovery still handle hardware faults, and the HyperPod training operator still handles job restarts.

NCCL 2.24 and later include the reliability, availability, and serviceability (RAS) subsystem, a small listener in each NCCL process that reports the state of the job’s communicators. For jobs that opt in, the agent reads this report from every pod every 30 seconds.

By default, NCCL binds the RAS listener to localhost inside the pod, where the agent can’t reach it. To opt a job in, you bind the listener to the pod IP instead. That makes port 28028 reachable on the pod network, which NVIDIA’s documentation notes has security implications. Before you turn it on, apply a Kubernetes NetworkPolicy that allows TCP port 28028 only from the agent’s pod and still allows traffic between the job’s own pods. The agent’s documentation includes an example policy. Then set NCCL_RAS_ADDR in the training container:.

To confirm the setting, turn on NCCL debug logging with NCCL_DEBUG=INFO and NCCL_DEBUG_SUBSYS=INIT,RAS. Each rank then logs the address RAS listens on:.

If the address is ::1 or 127.0.0.1, NCCL_RAS_ADDR isn’t set and the agent can’t reach the listener.

Recent findings suggest that for each monitored job, the agent combines the per-pod results into a job-level state. The job is healthy when every pod returns a valid report, degraded when only some do, and unhealthy when none do. Unhealthy usually means the training processes have stopped.

A training job can hang without exiting. An NCCL timeout, a stalled data pipeline, or a deadlock can leave the job holding its GPUs while Slurm still indicates it as running. It stays that way until someone notices that the loss or the log has stopped changing. Teams that run Slurm often build their own watchdog scripts and alarms to catch these jobs, and then need to maintain them.

Today, we’re launching hung job detection for SageMaker HyperPod Slurm clusters. It finds these jobs, writes an event to CloudWatch, and can cancel a hung job so that Slurm puts it back in the queue. You turn it on for each job with an environment variable that points to a small rules file. It needs no changes to your training scripts or containers, and it works with PyTorch, TensorFlow, JAX, and custom scripts.

According to recent reports, hung job detection runs as an agent on every node and is off by default. The agent watches only jobs that set the HYPERPOD_HANG_RULES environment variable to the path of a rules file. The rules file decides how the agent detects a hang:.

When the agent declares a hang, it writes a HANG_DETECTED event to CloudWatch. If the rules file sets the action to cancel, the agent also cancels the job and Slurm requeues it. With the default action, notify, the agent writes the event and leaves the job running.

According to recent reports, hung job detection is separate from auto-resume, which restarts jobs that exit after a hardware failure. Auto-resume handles jobs that crash and hung job detection handles jobs that keep running without making progress.

It has been revealed that on HyperPod clusters orchestrated by Amazon EKS, HyperPod already detects hung jobs in two cases. The HyperPod training operator checks the logs of each HyperPodPyTorchJob against rules in the job specification and restarts the job when it hangs. The same rules can also restart a job whose throughput drops or whose loss spikes. You don’t need Ray for this. For Ray Train jobs, HyperPod hung job detection for Ray watches every worker by default, with no changes to your code.

According to recent reports, the agent uses whatever rules file a job points to and doesn’t check who owns it. Anyone who can edit the file, or replace it in its directory, can change detection for every job that uses it, including making the agent cancel those jobs. The chmod 600 in the example keeps a personal rules file private to its owner. For a file that a team shares, use chmod 644 so the team can read it and only its maintainer can edit it. In both cases, make the parent directory writable only by its owner so nobody can swap the file.

It has been revealed that by default, the agent reads the job’s Slurm output file. To watch a different file, set monitoring.log_file. To cut false positives, set metric_evaluation_data_points on a rule so that several 10-second checks in a row must fail before the agent declares a hang. A rules file can have up to 20 rules and be up to 1 MB.

To turn off detection for a job that would otherwise inherit HYPERPOD_HANG_RULES, add --no-hang-detection to srun, or to sbatch to cover every step in the job. To turn it off for every job that uses a rules file, set "enabled": false in the file. Running jobs keep their current settings, and the change applies to jobs you submit afterward.

It has been revealed that node health is essential to reliable distributed training, but it does not provide a complete picture of workload health. MultiNodeTrainingValidation detects instances that pass hardware diagnostics but produce invalid training results. The HyperPod Kubernetes Resource Monitoring Agent connects Kubernetes infrastructure failures to the jobs, pods, and nodes involved. Hung job detection identifies Slurm jobs that remain active after they stop making progress and can return them to the queue automatically.

Recent findings suggest that together, these capabilities help you detect failures earlier, shorten investigations, and raise goodput by reducing the GPU time spent on workloads that can’t make useful progress. Use MultiNodeTrainingValidation when adding or revalidating capacity, run the HyperPod Kubernetes Resource Monitoring Agent continuously on supported Amazon EKS clusters, and begin hung job detection in notify mode before you switch to automatic cancellation. To get started, see the SageMaker HyperPod resiliency documentation for Amazon EKS and the hung job detection documentation for Slurm.
