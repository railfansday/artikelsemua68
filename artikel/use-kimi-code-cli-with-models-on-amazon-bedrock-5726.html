Kimi Code CLI is an open source coding agent from Moonshot AI, the creator of the Kimi series of open-weight foundation models. Previously, using Kimi Code with models on Amazon Bedrock meant configuring a generic connection “provider” with an Amazon Bedrock API key. For many AWS customers, this meant introducing an extra credential to obtain and protect.

With v2.7.0, Moonshot AI adds a native bedrock provider to the CLI. You can now configure the agent to use your standard AWS credential chain, including named profiles and single sign-on (SSO), instead of creating and managing a separate API key.

Industry observers note that in this post, we show you how to connect Kimi Code CLI to models on Amazon Bedrock using your existing AWS credentials. We use Kimi K3.1 Pro Highspeed as an example, which supports streaming, configurable reasoning, image input, and client-side tool calling.

In a recent development, amazon Bedrock provides pay-per-token inference for a range of open and proprietary models from leading providers, available through standard APIs. Processing stays within the AWS data boundary, as detailed in the Data protection section of the User Guide. The model cards detail which APIs and features are supported for each model.

In a recent development, in older versions of the Kimi Code CLI, you could connect to Amazon Bedrock through a provider with type = "openai" or type = "openai_responses". These use the OpenAI-compatible Chat Completions or Responses APIs, respectively. This approach required you to set the regional base_url and provide an Amazon Bedrock API key. The key could be short-term or long-term, but it was a separate credential for you to obtain and manage.

Edit config.toml directly to set up the Amazon Bedrock provider. For further details, refer to Model providers in the Kimi Code documentation.

Industry observers note that kimi Code doesn’t auto-detect the capabilities of most models on Amazon Bedrock, including Kimi models. Check the Amazon Bedrock model card for each target model and explicitly declare its capabilities to let Kimi Code make use of them.

For example, Kimi K3.1 Pro Highspeed supports always_thinking, thinking, image_in, and tool_use, but not audio_in or video_in, as reflected in the config.toml example shown earlier.

These declarations describe client behavior. You should only include capabilities that are supported for each target model and Amazon Bedrock API endpoint. Validate tool and image workflows for your application rather than relying on the capability labels alone.

The bedrock provider requires an explicit AWS_REGION or AWS_DEFAULT_REGION in Kimi Code’s config.toml or the shell environment. It can’t infer a Region configured only in ~/.aws/config or through aws configure.

According to recent reports, when you use cross-Region inference profiles (with prefixes such as global., us., or in.), the configured Kimi Code Region controls the source Region that receives your requests. For more information, refer to cross-Region inference in the Amazon Bedrock User Guide.

Industry observers note that for workloads without data-residency requirements, start with the global inference profile. This model, like many others, is priced 10% lower for global inference than through geographic profiles. Review Amazon Bedrock pricing for current rates and geographic alternatives.

In a recent development, in some cases, the provider’s auto-detection might mistake the API protocol or target URL you want to use for a particular model. For example, you will need to set a different URL to use Amazon Bedrock through a VPC endpoint or the Mantle endpoints.
