Industry observers note that coding agents such as Claude Code and OpenAI Codex CLI work in tasks. A developer asks for a change, and the agent reads files, edits code, and runs tests until the work is done. One task can take a few model calls or dozens. What the developer pays for is the task, not one call.

Recent findings suggest that the price per token alone doesn’t tell you what a whole task costs. The total depends on how many turns a model needs, how much history each turn replays, and how often a task has to be retried or never finishes. You pay for every attempt, including attempts on tasks that never finish. So when you route a coding agent’s requests between models, judge the routing by cost per solved task: the total cost of your runs divided by the number of runs whose tests pass.

NVIDIA NeMo Switchyard is an open source library that helps an AI agent choose which model handles each request. You define the models that it can use and the strategy that it follows. Its LiteLLM integration supports two strategies. Stage routing reads the recent tool activity and results in the request history, and then picks one of two candidate models. Random routing picks from the configured models, with optional weights, for traffic splits and A/B comparisons. Another option you can explore is LiteLLM, who also recently shipped a native built-in Switchyard stage router as an auto-router strategy.

Industry observers note that in this post, you use the AWS Cloud Development Kit (AWS CDK) to deploy LiteLLM, an open source gateway for large language models (LLMs), with the Switchyard routing plugin in your AWS account. LiteLLM calls the models on Amazon Bedrock. You then use the sample’s benchmark runners to measure cost per solved task for a routed model group and for single-model baseline groups, so that you can evaluate routing against your own workloads.

In a recent development, note: The sample installs switchyard-server 0.3.0 from crates.io and runs the published LiteLLM v1.102.0 image. NVIDIA documents switchyard-server 0.3.0 as a demo and evaluation component, and its configuration can change between releases. This sample uses the experimental Switchyard LiteLLM integration and its configuration and APIs may change between releases. This is sample code, for non-production usage. LiteLLM listens on port 4000 in the container and is the load balancer’s target, and the task’s security group admits only the load balancer. The path allowlist keeps the LiteLLM admin UI, API docs, and key management routes unreachable. Amazon Elastic Container Registry (Amazon ECR) holds the gateway image. AWS Secrets Manager generates the secret behind the gateway key, and the container adds the sk- prefix when it starts. The task definition passes the profile files in LITELLM_CONFIG_TEXT and SWITCHYARD_CONFIG_TEXT, and the startup script writes them to /tmp before it starts LiteLLM. Logs go to one Amazon CloudWatch log group, //litellm, which keeps them for 30 days, and Container Insights collects metrics. The VPC spans two Availability Zones, and one NAT gateway provides outbound access for image pulls and other AWS services.

The plugin supports Stage routing, which needs exactly two candidates, and Random routing, which needs at least two and splits traffic by weight for A/B tests. Classifier-backed strategies, such as Task and Composite routing, need intermediate model calls that this integration doesn’t support. See the Switchyard routing overview for the full catalog.

In a recent development, after the runs, the runner prints one row per model group, with RUNS, SOLVED, ERRORS, COST/TASK, and COST/SOLVED columns. Cost per solved task is the estimated cost of all runs on a group divided by the runs whose tests passed. The runner prices each turn from the model in its x-litellm-model-name header and the token usage in the response, using the PRICES table in bench/run.py. A turn with cached input, a model without a PRICES entry, or a response without the header or token counts stays unpriced instead of counting as zero. Add a PRICES entry when you add a model to a profile, and check Amazon Bedrock pricing for current prices. A few runs on two tasks demonstrate the workflow. They aren’t enough to draw conclusions about cost or quality.

A group highlights n/a with the reason when any of its runs is unpriced, and COST/SOLVED shows - when no run was solved. To see where the cost went, check the turns: the terminal prints the model that served each turn, and the transcript under bench/results/ records it.

The runners execute model-written Python on your machine. The subprocess that runs the tests has no credentials in its environment, but it isn’t an operating system sandbox: the code can read any file that your user can read and can reach the network.
