From first endpoint to global fleet: 14 more launches for managed endpoints and HyperPod Inference.

In September, Amazon SageMaker Inference: 2026 year-to-date introduces in review covered 13 launches that shortened the path from a model to a production endpoint. Most of them answered one question: how do I get this model serving promptly and reliably? This post covers the 14 launches that came next, bringing the total for 2026 to 27.

According to recent reports, once a model is in production, the questions change. Teams want to know which configuration the model should run on now that traffic is real, how to fit more models onto GPUs they already pay for, what to do when the next model is too large for one machine, why requests wait in one Region while GPUs sit idle in another, and why latency rose when nobody changed anything. This post takes those questions in the order teams usually meet them.

For HyperPod Inference, it listed additional routing strategies, broader support for model serving frameworks, and expanded multi-Region networking. The Inference Gateway and the Global Inference Gateway deliver the routing and multi-Region work, and managed NVIDIA Dynamo is a newly introduced serving framework. For managed endpoints, the roadmap pointed to deeper integration with the rest of the AWS AI landscape. Inference recommendations now run from Amazon SageMaker AI Studio, the SageMaker Python SDK, and the coding agents engineers already use, and endpoints can now route requests across Regions and accounts.

To keep each section concrete, we follow one hypothetical team through the blog post. In the spring, they launched a customer support assistant on a 70B-parameter model behind a single SageMaker AI endpoint, using the launches from part 1. By the fall, they need to support more product lines, adopt a larger reasoning model, serve customers in a second Region, and keep their GPU bill flat.

The team picked its first configuration from a benchmark run in April. Since then, they have added four LoRA (Low-Rank Adaptation) adapters, one for each product line, and the product team has set a target of 500 milliseconds for time to first token (TTFT) at peak load. The April configuration was never tested against either change. The engineers who will re-run the analysis work in notebooks and coding agents, and few of them use the console.

Inference recommendations released in April as an API. Four updates since then make it available in more of the places teams work, and let it answer two harder questions: how many adapters an endpoint can carry, and how much concurrency it can take before it misses a latency target. A fresh agent skill brings the same expertise into coding agents.

Blog: Launching UI for generative AI inference recommendations in Amazon SageMaker AI.

The April launch automated instance, container, and optimization selection through APIs. Inference recommendations are now also available in SageMaker AI Studio as a guided, low-code workflow. In Studio, choose Jobs, then Inference optimization. Choose a use-case profile (Interact, Generate, Summarize, or Custom), an optimization goal (minimize latency, maximize throughput, or minimize cost), and a model from SageMaker JumpStart, Amazon Simple Storage Service (Amazon S3), the Model Registry, or an existing SageMaker model.

SageMaker AI benchmarks candidate configurations on real GPU infrastructure using NVIDIA AIPerf and applies techniques that match the goal, such as speculative decoding for throughput or kernel tuning for latency. You compare the ranked results by TTFT, inter-token latency, throughput, and cost, and then deploy the chosen configuration to a real-time endpoint from Studio.

Blog: LLM optimization integration for Amazon SageMaker Python SDK.

It has been revealed that benchmarking and recommendations previously required SageMaker AI Studio or direct Boto3 calls. They are now part of the SageMaker Python SDK v3 (version 3.17.0 and later), the same interface teams use for training and deployment, so the workflow fits into notebooks, CI pipelines, and MLOps workflows. You can benchmark a live endpoint against your workload traffic, generate ranked recommendations for a latency, throughput, or cost goal, and deploy the top-ranked configuration to a real-time endpoint in a single call.

The SDK also supports longer workflows. You can run recommendation jobs in parallel to compare serving frameworks such as LMI and vLLM, and you can resume from a completed job so that deployment happens in a different notebook or pipeline stage without re-running the benchmarks.

Developer guide: Get recommendations for models with LoRA adapters.

Industry observers note that many teams use LoRA adapters to specialize one foundation model for several use cases. Each adapter kept in GPU memory reduces the number of concurrent requests the endpoint can serve, and the right balance depends on the instance type, the number of adapters, and the traffic profile.

It has been revealed that inference recommendations now accept adapters as Model Package Amazon Resource Names (ARNs), for adapters produced by SageMaker fine-tuning, or as S3 URIs, for adapters from external pipelines such as Hugging Face PEFT. SageMaker AI benchmarks combinations of adapter count and concurrency on real GPU infrastructure and returns ranked results for your workload. The output lists both formats for every adapter. The recommended deployment uses SageMaker Inference Components, with one component for the base model and one for each adapter, so you can add, update, or remove an adapter without disrupting the base model or the other adapters.

Blog: Right-size generative AI endpoints with concurrency sweeps on Amazon SageMaker AI.

According to recent reports, right-sizing an endpoint means finding the highest concurrency it can sustain without breaching latency or error targets. Until now, that meant picking concurrency levels by hand, running a sweep, checking the results against the service level agreement (SLA), and repeating with a narrower range whenever the model or instance changed.

Inference recommendations now include a search that finds that boundary directly. Set search_recipe to max-concurrency-under-sla and supply targets for any combination of maximum TTFT, maximum time per output token, maximum end-to-end latency, and maximum error rate. The benchmarking engine (AIPerf) starts from a broad range, narrows it based on which probes pass or fail, and converges in fewer iterations than a linear sweep. The result reports the largest passing concurrency (feasible_max) or, if no level qualifies, the smallest failing one (infeasible_min).

The search uses the same CreateAIWorkloadConfig and CreateAIBenchmarkJob APIs as concurrency sweeps. Optional parameters (concurrency_min, concurrency_max, search_max_iterations, and search_initial_points) bound the cost and speed up convergence.

It has been revealed that the support assistant does not run alone. An embedding model, a reranker, and a small classifier that routes tickets live in the same account, and each uses a fraction of a GPU. On a standard endpoint, each model copy still held a whole accelerator, so the team ran out of placement slots while GPU memory sat unused.

Every create, resize, and scaling policy had to be scripted, and there was no single view of what each model was using.

Blog: SageMaker Inference now supports Multi-Instance GPU to maximize GPU utilization for model endpoints.

In a recent development, GPU partitioning uses NVIDIA Multi-Instance GPU (MIG) technology to divide one physical GPU into as many as seven partitions, depending on the accelerator. Each partition has dedicated GPU compute and memory, with complete hardware isolation. You define the partition layout when you create an endpoint for inference components and choose a partition type for each component. Applications keep invoking models by inference component name, so client code does not change.

According to recent reports, MIG isolates GPU compute and memory between partitions. Models on the same instance still share host CPU, host memory, networking, storage, and endpoint routing. You pay the standard rate for the full instance-hour, so the saving comes from placing more models on each instance, not from a lower hourly price.

For the support team, the embedding model, the reranker, and the classifier now run in separate partitions of one GPU on a single endpoint, and the team manages every component, including the assistant and its adapters, from the console.

The team’s next model is a reasoning model whose weights alone exceed the GPU memory of any single instance. They have also noticed that long, retrieval-heavy prompts slow token generation for every other user on the endpoint. For a model this size, they move the workload to HyperPod Inference, which gives them dedicated clusters and Kubernetes-native control. The support assistant stays on managed endpoints.

Blog: Managed NVIDIA Dynamo on Amazon SageMaker HyperPod Inference.

Sources indicate that part 1 covered two building blocks for large models on HyperPod: disaggregated prefill and decode in Inference Operator v3.2, and KV-aware routing as part of the managed tiered KV cache. This launch adds multi-node serving and changes who operates the stack. NVIDIA Dynamo is an open source inference framework that provides multi-node sharded serving, disaggregated prefill and decode, and KV-aware routing. Teams could already run Dynamo on their own Kubernetes clusters, but they had to build and operate everything around it: placing all the nodes of a replica together, wiring Elastic Fabric Adapter (EFA) networking so prefill can hand its KV cache to decode at hardware speed, maintaining serving images, and recovering when one failed node takes down a multi-node replica.

In a recent development, with this launch, Dynamo runs as a managed serving engine on HyperPod. Dynamo makes the serving decisions: how the model is sharded, how prefill and decode are split, and where each request goes. HyperPod provides what those decisions depend on:.

There are three ways to start. Teams running Dynamo on self-managed Kubernetes can bring their existing DynamoGraphDeployment (DGD) manifests largely unchanged. Teams already on HyperPod Inference can update the add-on and add a short dynamoSpec block to an existing InferenceEndpointConfig, which HyperPod converts into a DGD, while existing endpoints keep serving. Teams latest to both can create a cluster with the add-on and Dynamo enabled from the console. In each case, clients call a standard OpenAI-compatible endpoint, so client code does not change.

Managed Dynamo supports vLLM, SGLang, and TensorRT-LLM, and is available in the Regions where Amazon SageMaker HyperPod is available.

Blog: Amazon SageMaker AI real-time endpoints now support KV cache aware routing.

Applications with long prompts or multi-turn conversations repeat a large prefix across requests. A model server can reuse the matching KV cache, but only if the next request reaches the instance that holds it. Prefix-aware routing, covered in part 1, fingerprints the start of each prompt and sends matching prompts to the same instance. Because it works from request history, its view of each instance’s cache becomes less accurate as the model server adds and evicts entries.

Sources indicate that KV-cache-aware routing uses the cache state the model container reports. The container publishes cache creation and eviction events to a central cache index, and SageMaker AI routes each request to an eligible instance that holds the longest matching cached prefix. This raises cache reuse for long-context prompts, multi-turn conversations, and workloads that share dynamic prompt prefixes.

In a recent development, it works with single-model endpoints and endpoints that use inference components, including LoRA adapters. It supports InvokeEndpoint, InvokeEndpointWithResponseStream, and the OpenAI-compatible API for Completions and Chat Completions payloads. You turn it on in the endpoint configuration. The first release requires an AWS-verified model container that implements the cache-event, tokenization, metrics, and OpenAI-compatible interfaces. You can track KV cache hit rate in detailed inference observability.

Recent findings suggest that which one to use. Prefix-aware routing works with any container and needs no container changes. KV-cache-aware routing needs a verified container and tracks the actual cache, which helps most when prefixes vary or caches turn over quickly.

Blog: Introducing Amazon SageMaker HyperPod Inference Gateway.

Inside a HyperPod cluster, capacity and demand rarely line up. One pod can be partway through a long-context request with its KV cache nearly full, while the next pod sits idle or already holds the prompt prefix or LoRA adapter the next request needs. Without visibility into that GPU state, new requests queue behind busy pods, and teams add GPUs to protect latency instead of using the ones they have. Each model also had its own endpoint, so clients had to track one endpoint per model.

Recent findings suggest that the Inference Gateway is a GPU-aware router that installs with the HyperPod Inference Operator add-on and gives each cluster one OpenAI-compatible endpoint for all of its models. For each request, it reads live signals from every model pod and picks the best one, with weights you can tune per workload:.

In a recent development, compared with round-robin routing, it reduced P99 TTFT by up to 97% on mixed GPU generations and by up to 98% under bursty traffic. It is available in all Regions where SageMaker HyperPod is available.

Blog: Introducing Amazon SageMaker HyperPod Global Inference Gateway.

Recent findings suggest that the Inference Gateway routes within a cluster, and each cluster can serve only the requests sent to it. A request can wait on a saturated cluster in one Region while GPUs sit idle in another. Clients had to choose a cluster themselves, and when a cluster failed, an engineer had to move traffic by hand.

The Global Inference Gateway gives teams one SageMaker-managed endpoint across every cluster they register. For each request, it scores clusters on queue depth, free KV cache, proximity to the caller, and recent error rate, and sends the request to the best one over the AWS private backbone. The Inference Gateway in that cluster still picks the pod. Requests authenticate with SigV4 and IAM. When a cluster becomes saturated or unhealthy, traffic shifts to the next-best cluster in under 30 seconds with no action from the client, and the cluster rejoins the pool when it recovers. Routing weights are tunable, with defaults if you leave them unset.

Recent findings suggest that adding or removing a model or cluster does not change anything for the applications that call the endpoint. No cluster is reachable until you publish it, and the published resources stay in your account. The Global Inference Gateway is available in the Regions listed in the AWS documentation.

You group endpoints that serve the same model under a routing target, and the application invokes the target instead of a specific Regional endpoint. The router does not add capacity, replicate models, or deploy endpoints, and the existing invocation path keeps working.

Blog: Amazon SageMaker AI now detects latency drift, idle GPUs, and missed optimizations on your inference endpoints.

According to recent reports, amazon SageMaker AI now continuously monitors your generative AI inference endpoints and tells you when a change could improve performance or lower cost. Monitoring is on by default for SageMaker AI inference endpoints, with no setup required, and you can opt out of endpoints. SageMaker AI looks only at operational signals: latency, GPU utilization, and the endpoint’s serving configuration. It does not read your requests or responses. When a finding clears its confidence threshold, a notification appears on the AWS Management Console, and the same message arrives by email for teams that work in notebooks and the CLI. The recommended action opens the SageMaker AI agentic experience in SageMaker AI Studio with the finding already filled in, so the analysis, the comparison, and the deployment change happen in one conversation. Nothing deploys until you apply it, and you can turn monitoring off at any time.

There are three types of findings:.

A standard rolling revision replaces an endpoint one batch at a time, and every batch runs on newly provisioned instances. On a large GPU fleet, that means finding new capacity at every step, and an update can fail partway through when the next batch of instances is not available. Each released instance must also finish cleanup before it can be used again, which slows the rollout.

SageMaker AI now updates models in place. It provisions one small batch of additional instances at the start, shifts traffic to that batch, and then updates the instances it frees, reusing them to roll the change across the rest of the fleet. The patch still rolls out in stages, but it needs new capacity only once. For a fleet of 20 instances with a batch size of 2, the update acquires 2 new instances instead of 20. Customers do not need to change anything. As with container caching in part 1, the improvement applies automatically to rolling model updates.

Figure 6: A rolling update acquires newly introduced instances at every step. An in-place rolling update acquires one batch at the start and reuses the rest of the fleet.

Recent findings suggest that for the support team, a Drift Watch finding quantifies the TTFT regression and opens a latest recommendation job against recent traffic. They roll out the updated model with one batch of extra instances, instead of finding new GPU capacity for every instance in the fleet.
