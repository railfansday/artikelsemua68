Introducing Amazon SageMaker HyperPod Global Inference Gateway: One endpoint across Regions and clusters

Recent findings suggest that during a traffic peak, a request can sit in a queue on a saturated HyperPod cluster while GPUs on another cluster, sometimes in another AWS Region, sit idle. You have already paid for that capacity, but your requests can’t reach it.

In Introducing Amazon SageMaker HyperPod Inference Gateway, we demonstrated how the Inference Gateway gives each Amazon SageMaker HyperPod cluster a single, GPU-aware endpoint. It reads real-time signals such as key-value (KV) cache utilization and queue depth to place every request on the best-suited pod. That solves routing inside one cluster, but not across clusters.

Today, SageMaker HyperPod introduces the Global Inference Gateway. It is one SageMaker-managed gateway that routes across every cluster you register, in one Region or across Regions. The gateway picks the cluster and carries the request over the AWS backbone, with automatic failover and authentication through AWS Signature Version 4 (SigV4) and AWS Identity and Access Management (IAM). Inside each cluster, the Inference Gateway keeps picking the pod, unchanged. The Global Inference Gateway is the second tier of the architecture we described in part 1.

Recent findings suggest that models are getting larger, and the GPU capacity to serve them is harder to find. To get enough of it, you spread it across more clusters and more Regions.

Recent findings suggest that consider a team that serves four models across five HyperPod clusters in two Regions. Without the Inference Gateway, clients track 20 endpoints: one per model per cluster. The Inference Gateway cuts that to five, one per cluster. But each client still picks a cluster itself.

The team needs one endpoint that sends each request to the best-suited cluster and moves traffic off a failed cluster on its own.

The Global Inference Gateway helps you get more from the GPU capacity you already have, with less to operate.

It has been revealed that “At Bagelcode, we run our own LLM inference service on AWS to help teams across the tech giant, including our game teams, use AI to improve how they work. In our beta tests, the Global Inference Gateway in Amazon SageMaker HyperPod routed requests across two AWS Regions through a single endpoint and kept serving them when one cluster could no longer serve the model. That gave our small platform team cross-Region failover without having to build or maintain our own routing layer.”.

— Jinhyung Park, VP (AI Platform), Bagelcode.

Setting up the gateway takes two decisions: which clusters to open up for routing, and which of them to group behind one gateway.

A cluster is reachable only after you publish it. When you publish a cluster, the controller creates a Network Load Balancer in front of the cluster’s Inference Gateway, publishes a virtual private cloud (VPC) endpoint service on it, and uploads the listener’s certificate to your TLS bucket. These resources live in your account. If you list a cluster in a gateway before you publish it, the call fails with a message that tells you what to fix.

(2) The gateway authenticates the caller and picks the best cluster. (3) AWS PrivateLink carries the request to that cluster, in the same Region or another, and (4) the cluster’s Inference Gateway routes it to a model pod, as it does today.

On each cluster, a service-managed metrics publisher with its own IAM role sends the cluster’s load to the gateway.

For each request, the gateway scores every healthy cluster on four signals and sends the request to the highest-scoring cluster. Each cluster’s metrics publisher supplies the load signals.

It has been revealed that your path depends on what you run today. If you serve from a single cluster, stay on that cluster’s Inference Gateway endpoint. Move to the Global Inference Gateway when you add a second cluster.

To set up the Global Inference Gateway, you prepare each cluster, create an execution role, and call CreateGlobalInferenceGateway. You then send OpenAI-compatible requests, signed with SigV4, to the gateway endpoint. For step-by-step instructions, including the IAM roles and policies, see the AWS documentation.

Every request to the gateway is signed with SigV4 and authorized with IAM. Callers need permission to invoke the gateway, and streaming has its own action:.

Sources indicate that attach this policy to each IAM identity that sends requests. To allow every gateway in the account, use global-inference-gateway/* as the resource.

Industry observers note that the execution role follows least privilege. It can describe only the clusters you list, reach only their Amazon Elastic Kubernetes Service (Amazon EKS) API, and read only the routing certificates under the gig/ prefix of your TLS bucket, tagged as created by HyperPod Inference.

If your clusters check JSON Web Tokens (JWTs), pass the token with --customer-identity-token (the X-Amzn-SageMaker-Customer-Identity-Token header), with no Bearer prefix. The token travels inside the SigV4 signature, so an unsigned token is rejected with 403 and a repeated token with 400. Turn on JWT checks on every cluster that serves a model, or on none of them, so a request doesn’t succeed on one cluster and fail on another.

Sources indicate that the gateway validates the cluster and starts routing to it once it is healthy. The endpoint, other clusters, and clients aren’t affected.

Call RemoveInferenceGateway in the gateway’s Region:.

The gateway stops sending latest requests to the cluster, lets in-flight requests finish, and removes the private endpoint. A gateway always keeps at least one cluster. To withdraw the cluster fully, set globalRouting.enabled: false in its InferenceGatewayConfig and reapply it.

Call DeleteGlobalInferenceGateway:.

In a recent development, the gateway endpoint stops serving, and per-cluster endpoints keep serving. After the gateway is deleted, withdraw each cluster with globalRouting.enabled: false, then delete the execution role and the IAM permissions you added for global routing.

In this post, we introduced the Amazon SageMaker HyperPod Global Inference Gateway: one SageMaker-managed endpoint across your HyperPod clusters, in one Region or several. The gateway picks the cluster based on KV cache headroom, queue depth, Region proximity, and error rate, and moves traffic off a failed cluster with no client changes.

The Global Inference Gateway is available in 13 AWS Regions: US East (N. Virginia), US East (Ohio), US West (N. California), US West (Oregon), South America (São Paulo), Europe (Frankfurt), Europe (Ireland), Europe (London), Europe (Stockholm), Asia Pacific (Tokyo), Asia Pacific (Mumbai), Asia Pacific (Singapore), and Asia Pacific (Sydney).

To get started, see the AWS documentation.
