According to recent reports, across Latin America, India, and Southeast Asia, WhatsApp is one of the most widely used messaging applications. That makes it an obvious place to build an AI agent. For many end customers, it is how they expect to interact with businesses. However, it is also a genuinely difficult surface to build for, even when your agent already runs on Amazon Bedrock AgentCore.

The agent is rarely the hard part. The integration is. Inbound messages arrive as deeply nested, type-dependent payloads that must be authenticated and normalized before your agent can read them. Media such as voice notes, images, and documents each require their own processing pipeline. Beyond message handling, you need conversation memory that survives sessions, durable schedules for reminders, and an authenticated path for external systems to trigger outbound messages. And anything you send more than 24 hours after the end user’s last message must use a pre-approved Meta message template.

Wiring that up means configuring more than 10 AWS services and learning a set of WhatsApp system behaviors that most teams discover only by hitting them. None of it is visible to a customer, but all of it has to work. Most teams either build it from scratch or hand the integration to a third-party service.

SMART (Social Messaging Agent Runtime Toolkit) is a third option: an open source Python SDK and Terraform stack that gives you the full channel layer. You provide an agent that runs on Amazon Bedrock AgentCore runtime, and SMART handles the rest. One command deploys the entire infrastructure to your AWS account.

Teams are already running on SMART with Amazon Bedrock AgentCore. Webmotors, originally scoped as a two-month engagement, compressed delivery to six weeks and moved their internal team into controlled production ahead of a full launch.

Whether you are starting from scratch or migrating an existing agent, you own the agent’s logic. You let SMART handle the channel.

Amazon Bedrock AgentCore is a platform to build, connect, and optimize agents at scale, with any framework or model. SMART builds on two of its main capabilities:.

Because AgentCore is framework-agnostic, so is SMART. Strands Agents gets memory wired automatically. LangGraph, Pydantic-AI, or another framework that gives you control over the conversation loop can integrate too. The SDK exposes the same memory and session hooks regardless of framework. You keep full control over the elements that differentiate your product: framework, model, prompt, and business logic.

The contract between SMART and your agent is deliberately small. Your agent receives the inbound message and returns text, optionally with rich message attachments. Everything else, session wiring, memory binding, delivery scheduling, is handled for you.

Industry observers note that the SMART core stack is organized into distinct layers: message processing, an agent layer, and a service layer. AWS End User Messaging Social receives inbound WhatsApp messages and routes them to the processing layer. An AWS Lambda function handles the channel logic, while Amazon Bedrock AgentCore provides the runtime, memory, and observability for the agent itself. Supporting services such as Amazon DynamoDB (optional, for per-user state), AWS Secrets Manager, Amazon CloudWatch, and Amazon Simple Storage Service (Amazon S3) supply state management, credentials, monitoring, and storage across the stack.

It has been revealed that inbound events arrive through Amazon Simple Notification Service (Amazon SNS). On each event, the webhook Lambda function verifies the SNS message signature, normalizes the payload, and rate-limits each user (20 messages per minute by default, with the DynamoDB state table enabled). It then fires a read receipt and typing indicator, so the conversation feels alive before the model finishes. Voice notes go through Amazon Transcribe. Other media becomes a descriptor or goes to a hook you register if you want custom handling. When the agent throttles or fails, the user receives a readable message that you can customize, rather than silence.

Agents built on SMART interact directly with end users, so production deployments should include appropriate safeguards. The Terraform stack creates and configures an Amazon Bedrock Guardrails resource by default. With a single guardrail variable in your environment configuration, you can use the stack’s default guardrail, bring your own, or opt out entirely. The controls that you apply are up to you. SMART makes sure the wiring is already in place.

According to recent reports, after the message is ready, the webhook function passes it to AgentCore runtime. AgentCore memory maintains conversation context across sessions, and AgentCore Observability, a capability of Amazon Bedrock AgentCore, traces every step for debugging and audit.

The webhook function sends the reply and messages your tools queued during the turn. A notification function handles sends outside a turn, such as proactive or scheduled messages. External systems trigger your event handlers by posting to an Amazon API Gateway endpoint protected by an API key and a Lambda authorizer. The event is published to Amazon SNS and the event Lambda runs your handler. Amazon EventBridge Scheduler handles time-based outreach, such as reminders and recurring check-ins. With message templates managed through AWS End User Messaging, you can send structured notifications outside the 24-hour WhatsApp session window.

Start by cloning the repository and scaffolding a project.

The --blueprint flag selects a project blueprint. Three blueprints ship, and minimal is the default if you don’t pass an argument:.

Industry observers note that you get a project with your agent.py, socialagent.dev.yaml (the project’s deployment configuration), handler stubs for the webhook, notification, event, and scheduler paths, and a vendored copy of socialagent_runtime/. The personal assistant and appointment-scheduler blueprints also bring tools, skills, and a templates.yaml for your message templates. minimal ships none of those, so you add them as required.

Next, iterate locally, with no infrastructure at all.

The socialagent dev command runs your real agent loop and real tools in a terminal read-eval-print loop (REPL), with AWS channel I/O stubbed. Memory becomes a local file-backed session, and state becomes a local JSON file shared across your dev sessions. Notifications print to the terminal, including buttons and list rows. One-shot schedules run immediately. Recurring ones are registered but do not fire. Tool calls appear inline. The reply arrives as one message, as on WhatsApp. The /event and /schedule commands exercise the handler paths. No deployment is involved, so you can test a change as soon as you save it.

Industry observers note that two caveats apply. The model call is real, so a blueprint other than minimal needs AWS credentials and Amazon Bedrock access. The REPL also doesn’t simulate IAM or Meta’s template review. Testing through a deployed stack is highly recommended before you consider something done.

In a recent development, you can add capabilities as recipes. Each recipe is a plain Python function plus a markdown skill that teaches the agent when to use it.

Wiring the recipe to the agentic layer is the developer responsibility, which is what keeps recipes portable if you change agent frameworks.

When the behavior is right locally, deploy the stack.

One step Terraform cannot do for you. AWS End User Messaging Social needs to know where to deliver inbound messages. Point your WhatsApp Business Account at the Amazon SNS topic the stack created. That setting lives on the business account, not in the stack. Point the WABA’s event destination at the stack’s SNS topic using the admin console’s Bind action, or with aws socialmessaging put-whatsapp-business-account-event-destinations from the CLI. Until it is linked, inbound messages go nowhere, and nothing errors.

When the project includes a templates.yaml, the deploy step also syncs your message templates with Meta. If you need to sync templates independently, run uv run socialagent templates sync, which reads the phone number ID and prefix from socialagent.dev.yaml and the template definitions from templates.yaml. A rejected template will fail the deploy, so fix the wording before retrying.

According to recent reports, meta sorts templates by purpose, and a transactional one has more permissive sending rules than a promotional one. Keep the wording plain. Emojis and marketing language are the usual reason a template gets reclassified as promotional. Running templates sync --force re-registers every template, sending approved ones back through Meta review. A plain sync skips them. Leave approved templates alone unless you need to change their content.

Now you’re ready to message your WhatsApp number.

Shipping one bot is a project. Operating a fleet of them is the part nobody budgets for, so you also get an optional administration console with its own Terraform root. Deploy it once. Each SMART stack that sets admin_registry_bucket registers itself to a shared Amazon S3 registry on deploy, and the administration console discovers those stacks from there.

Sign-in runs through Amazon Cognito, with multi-factor authentication (MFA) required. Role-based permissions are then enforced on every API route. The console itself is served from Amazon CloudFront over a private Amazon S3 bucket.

It has been revealed that the console runs on AWS services end to end. Every conversation stays within two providers: Meta and AWS. Model calls may be processed in other AWS Regions through Amazon Bedrock cross-Region inference. See docs/data-flows.md in the repository for details on inference routing, media processing, and service opt-out options.

To avoid ongoing charges, tear down the stacks in the following order.

Terraform will not remove three things. The media and audit S3 buckets block destroy while they hold objects, unless enable_force_destroy is set. Templates registered with Meta persist. Your phone number registration is account-level and stays in place.

When building a WhatsApp AI product, the agent is where your differentiation lives. The channel integration is what eats your roadmap. SMART moves that boundary for you. Write a prompt, a few tools, and your business logic. In return you get webhook ingestion, media handling, conversation memory, scheduling, and template management. All backed by one-command infrastructure, a local development loop, and an administration console running in your own AWS account.
