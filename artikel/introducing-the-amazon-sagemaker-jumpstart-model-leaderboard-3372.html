Recent findings suggest that amazon SageMaker JumpStart gives you hundreds of open-weight foundation models you can deploy rapidly. That choice is powerful, but it also creates a real question: Which model should you start with? Comparing models usually means reading model cards one at a time and hunting for benchmark scores that different sources published under different conditions. Then you still must guess how each model will perform, and what it will cost, for your use case.

In a recent development, today we are launching the Amazon SageMaker JumpStart Model Leaderboard, a fresh way to compare JumpStart models side by side on quality, speed, and cost, directly in Amazon SageMaker Studio. In this post, we explain what the leaderboard shows, define the key terms in plain language, and walk through how to go from a shortlist to a deployed model.

The leaderboard is a newly introduced view of the JumpStart base models page in SageMaker Studio, right next to the Categories and All models views. It uses the same search bar and filters you already know, and it opens on a leaderboard of large language models (LLMs). You see rankings immediately without answering setup questions first. For each model, it demonstrates two kinds of information:.

Recent findings suggest that because both kinds of numbers come from the same place and the same method, you can make a like-for-like comparison instead of stitching together data from different websites. At launch, the leaderboard covers 70+ models from providers including Meta, Google, Qwen, IBM, and Arcee, with more added over time.

This section defines the terms the leaderboard uses: the quality benchmarks, the use case profiles and optimization goals that shape the performance numbers, and the performance metrics themselves.

A benchmark is a standardized test: a fixed set of questions with known answers. Running every model through the same test gives you a score you can compare. At launch, the leaderboard reports three reasoning benchmarks for LLMs:.

Higher is better for all three. The leaderboard highlights each benchmark separately rather than blending them into one number. That keeps the results transparent: You can weigh the benchmarks that matter for your application and check each score against the public definition of the benchmark.

Sources indicate that speed and cost depend on your workload and on how the model is deployed. Two menus above the leaderboard control which performance and cost numbers you see:.

In a recent development, A note on cost: Estimated cost reflects SageMaker instance cost only, based on the on-demand hourly rate for the configuration’s default instance type. It does not include data transfer, storage, inference component costs, or discounts such as Reserved Instances or AWS Savings Plans. Your actual bill will vary. The following steps show how to go from browsing to a deployed model. You need access to SageMaker Studio and permission to deploy JumpStart models.

In SageMaker Studio, open the Models page, then select the Leaderboard view. The leaderboard keeps the same search bar and filters as the other views, and it has its own URL. You can bookmark it or share a direct link with your team.

The following screenshot demonstrates the Models page with the Leaderboard view selected.

Figure 2: JumpStart base models page with the Leaderboard view selected.

Use the same search and filters you already use elsewhere in JumpStart to keep only the models that fit your requirements. Common filters include license, provider, and input and output modality. Start with hard requirements, for example a license that allows commercial use, before you look at scores.

The following screenshot indicates the leaderboard filtered by input modality, output modality, and license.

Figure 3: Leaderboard with filters applied.

Industry observers note that above the leaderboard, select the profile closest to your workload from the View benchmarks for your use case menu (default: Max Context). Then choose a goal from the Optimized for menu (default: Balanced). For a chatbot your customers interact with, Latency optimized is a sensible start. For overnight document processing, Throughput optimized or Cost optimized may fit better. The performance and cost columns patch, and quality scores stay the same.

The following screenshots show the View benchmarks for your use case and Optimized for menus above the leaderboard.

Figure 4: View benchmarks for your use case menu.

In a recent development, each column has a blue heatmap, so the top-performing models stand out at a glance: the deeper the blue, the stronger the result in that column. Sort any benchmark column to rank models by the metric you care about most. Use the column settings (gear icon) to hide metrics you don’t need, and scroll horizontally to see more. The model name columns stay frozen as you scroll, and a fade at the edge demonstrates when more columns are available.

Figure 6: Heatmap and column settings.

Choose a model to open it. From there, you have options to deploy the model or, for models that support serverless customization, to customize it. If you deploy, choose the same use case and optimization goal you compared on the leaderboard. Each metric applies to the configuration it was measured on, and a different configuration can change quality, latency, throughput, and cost.

In a recent development, reading the table, Model A has the highest knowledge score but also the highest cost and the slowest first response. Model B scores almost as well, holds up on multi-step reasoning, and runs on a smaller, cheaper instance. For a help desk, where reasoning through a question and responding promptly matter more than the last few points of general knowledge, Model B is the better starting point. A bigger model is not always the better choice, and the leaderboard makes that trade-off visible in seconds.

From there, you would deploy Model B, test it with real questions from your help desk, and keep Model C in mind as a lower-cost option if quality holds up.
