Industry observers note that arisGlobal, a provider of life sciences technology spanning pharmacovigilance, regulatory, medical affairs, clinical, and quality functions, developed NavaX, an AI engine purpose-built for life sciences on Amazon Bedrock, to automate adverse-event case processing. ArisGlobal chose Amazon Bedrock for managed access to foundation models, EU geographic cross-Region inference, and managed prompt caching. As enterprise customers added distinct compliance requirements, the shared prompt prefix grew by about 150% over 6 months, while per-case inference costs increased by more than 200%.

Industry observers note that arisGlobal first cached each source document because it was the largest part of a request. That left the growing shared prompt prefix outside the cache. By reversing the order and caching the shared prefix instead, ArisGlobal reduced effective input cost and supported additional tenants without proportional cost growth.

ArisGlobal is the creator of LifeSphere, a unified SaaS platform for pharmacovigilance, regulatory affairs, quality, and medical information. LifeSphere serves pharmaceutical companies globally, including multiple Top 20 pharma organizations by revenue (source: ArisGlobal press release). The entire system runs on AWS.

Sources indicate that lifeSphere NavaX is ArisGlobal’s AI engine that transforms drug safety from a system of record into a system of strategic advantage. ArisGlobal productionized their first generative AI solution on Amazon Bedrock with Anthropic’s Claude in March 2025. According to ArisGlobal’s internal production telemetry, they have processed over 1 million real transactions in regulated pharmaceutical environments, handling billions of tokens across multiple enterprise tenants. When a pharmaceutical organization receives an adverse-event report, typically a multipage PDF describing a patient’s reaction to a medication, NavaX’s Dynamic Data Extraction (DDE) agent extracts around 130 fields. These fields include patient demographics, suspect drugs, reporter information, event timelines, seriousness criteria, and regulatory classifications. Because this content includes protected health information, ArisGlobal applies responsible-AI controls as a standard part of its production deployment. It draws on capabilities such as Amazon Bedrock Guardrails to filter content and detect or mask sensitive information. Extracted fields are also validated against the schema and grounded in the source document.

Industry observers note that two inputs repeat at different scopes. The shared prompt prefix includes the system rules, extraction schema, and few-shot examples. It repeats across requests, cases, and tenants using the same agent. The source document repeats only for the requests associated with one case.

According to recent reports, when NavaX rolled out with its first enterprise tenant, the system prompt was lean. As ArisGlobal onboarded additional pharmaceutical companies, each brought specific requirements:.

Sources indicate that over 6 months, the shared prompt prefix grew from approximately 72,000 to 180,000 tokens, a 150% increase. With multiple sequential requests per case, per-case inference costs increased by more than 200%.

The prefix grew with every tenant and was reprocessed on every request, so prompt growth compounded with transaction volume.

Amazon Bedrock prompt caching reduces latency and input token costs by caching a contiguous prompt prefix from the start of a request through a cache checkpoint. A later request with the same prefix can read cached tokens at a reduced rate instead of processing them again. Cache entries have a time-to-live (TTL) that resets after a successful cache hit.

Caching is prefix-based rather than block-based. Request sections are evaluated in sequence—tools, system, then messages—so changing an earlier section invalidates matching content that follows it.

Sources indicate that with explicit cache checkpoints, you can choose the exact prefix boundary. Supported Claude models allow up to four checkpoints per request.

Industry observers note that with simplified cache management, you place one checkpoint after static content. Amazon Bedrock searches backward from that point for the longest matching prefix, up to about 20 content blocks.

Industry observers note that arisGlobal uses one explicit checkpoint immediately after the shared prompt prefix, which is sent first. The per-case document follows the checkpoint and is processed on each request.

This reverses the initial request order. Because only a prefix can be cached, ordering determines which content can be reused.

The first design put the 10–200 page source document at the start of each request and placed the checkpoint after it. The shared prompt prefix and section-specific question followed the checkpoint.

The design reused the document within one case: the first request wrote it to cache, and later requests for that case read it at the reduced rate.

The next case used a different document and required a fresh cache write, so reuse never extended across cases or tenants.

It has been revealed that more importantly, the shared prompt prefix remained after the checkpoint and was processed at the full input rate on every request. The content driving the cost curve was excluded from the cache.

The production design changed the order rather than adding another checkpoint: the shared prompt prefix comes first, the checkpoint follows it, and the document comes last.

ArisGlobal gave up limited document reuse within one case and gained prompt reuse across the fleet. The shared prefix is also the part that grows as customers are added.

According to recent reports, for most active accounts, cases arrive about every 5 minutes per tenant and multiple tenants run concurrently. This traffic keeps the shared prefix warm during business hours because each cache hit resets the TTL.

A second checkpoint after the document would cache a combined prefix consisting of the shared prompt and that case’s document. The entry would still be unique to one case.

ArisGlobal therefore prioritized the prefix whose reads amortize across the fleet. The shared prompt prefix scales across cases and tenants. The per-case document does not.

ArisGlobal’s experience offers guidance for many workloads with large, repeated prompt prefixes:.

Recent findings suggest that cache what repeats, not what is largest. A large per-case document offers limited reuse, while a byte-identical shared prompt prefix can serve requests across the fleet.

Put stable content first. Order tool definitions, system instructions, schemas, and examples before the checkpoint. Place tenant identifiers, case data, and the per-request question afterward.

It has been revealed that use fleet traffic to amortize cache writes. Requests from tenants using the same agent can read the same prefix, and cache hits reset the TTL. For sporadic traffic, evaluate the 1-hour TTL on supported models.

Reduce avoidable calls. Each call still processes the uncached document, so bundle sequential questions when output limits and schema requirements permit.

Industry observers note that keep the prefix byte-identical. Timestamps, request IDs, tenant names, and reordered tool definitions can cause misses. Move every dynamic element after the checkpoint.

Monitor the production baseline. Track cache reads, cache writes, and total input tokens in CloudWatch. Alert on a sustained drop below the normal 65% cache-hit baseline rather than using an incompatible 80% threshold.

Check model-specific limits. Prefix minimums and TTL options vary by model. Claude Sonnet 4.5 requires at least 1,024 tokens for a cache checkpoint.

Recent findings suggest that arisGlobal combined EU geographic cross-Region inference with prompt caching aimed at the right content. Caching the stable shared prefix instead of the per-case document reduced effective input cost by approximately 50%, contributed to approximately 40% overall monthly inference savings, and supported around 15% more enterprise tenants without proportional cost increases.

Recent findings suggest that the key lesson is that cache value depends on reuse, not size. For multi-tenant agentic workloads, a repeated shared prompt prefix can be more valuable than a larger document that changes for every case.
