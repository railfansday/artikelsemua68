Introducing managed cluster extensions for observability and user management in Amazon SageMaker HyperPod Slurm

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Keeping a shared Slurm cluster for foundation model development in sync entails keeping several separately maintained pieces of configuration matched to what’s running on the nodes. The cluster’s shape lives on multiple configuration files, its software in custom scripts, its network topology in files that must be edited as nodes change, and its users in a roster that an administrator must maintain and rerun. Over time these pieces drift away from what’s actually running, and nothing tells you when they do.

We believe cluster configurations should be managed the way you manage the rest of your AWS infrastructure. You declare what you want through an API or the console, AWS validates it before it’s applied, the cluster is kept in that state continuously, and you can see whether it’s working. During 2026, Amazon SageMaker HyperPod brought that approach to Slurm clusters, with API-driven Slurm configuration, AMI-based configuration, continuous provisioning, automatic topology management, and deep health checks. Today, we launched cluster extensions, which bring the same approach to the software and settings on running nodes, with managed extensions for observability and user management. However, through all of it, you still keep full access to every node in your cluster, including the controller node. You can SSH in, configure nodes directly, and run your own lifecycle scripts. The APIs give you less to maintain, direct access gives you more control, and you choose the balance.

According to recent reports, in this post, we walk through the features we introduced in 2026 and explain why the software on running nodes needed a different mechanism. We then show how cluster extensions work, through both the API and the console, and follow a platform team through a quarter on a cluster that uses them.

In a recent development, we can think of a Slurm cluster’s configuration grouped into six layers. Five of them describe the cluster itself: its definition, node setup, capacity, network topology, and hardware health. The sixth covers the software running on its nodes, which we discuss in the next section. The following figure shows the six layers.

Earlier in 2026, we brought declarative management to the first five layers. With API-driven Slurm configuration, administrators define node roles, partitions, and Amazon FSx for Lustre and Amazon FSx for OpenZFS mounts in CreateCluster and UpdateCluster requests, and connect an external accounting database. HyperPod updates partition settings while preserving other controller-node Slurm customizations. AMI-based configuration replaces routine setup scripts with images preconfigured with Slurm, Docker, Enroot, Pyxis, and home directories. A custom AMI or OnInitComplete script handles organization-specific software. Continuous provisioning for Slurm retries capacity requests in the background; AMI-based configuration works with it, minimum capacity requirements let teams specify MinInstanceCount, and cluster operations track scaling requests.

Industry observers note that automatic topology management maintains the network layout as nodes scale or are replaced. On Slurm 25.11 or later, partition-level topology supports tree or block topology per partition. For hardware health, on-demand deep health checks stress GPUs and test NVIDIA Collective Communications Library (NCCL) connectivity, while deep health checks with continuous provisioning run as nodes are provisioned. Nodes under check stay in Slurm maintenance reservations until checks finish, keeping jobs off them.

In a recent development, the five layers described so far are configurations that HyperPod can derive or apply once, when it provisions a node. The sixth layer, the software that runs on the nodes, behaves differently because it keeps changing for the life of the cluster. As researchers join and leave, a team asks for deeper GPU metrics for a week, and an exporter ships a fix. For this layer, lifecycle scripts have been the main mechanism so far, and they have drawbacks when the software keeps changing. A script runs only when a node is provisioned, so each change means editing it and then replacing nodes or rerunning it across the fleet. A mistake indicates only when the script runs on a node, and nothing reports what’s installed, so nodes drift apart over time.

In a recent development, we wanted the software to be declared in one place, checked when you submit it, kept consistent across nodes, and visible afterward. In November 2026, we rolled out cluster extensions, which are software packages managed by AWS that you install, configure, update, and remove through APIs or the Amazon SageMaker AI console, starting with observability and user management, including directory integration, as the first software extensions. Recent findings suggest that you can use cluster extensions from the SageMaker AI console or through an API. On the console, the Extensions tab on a cluster’s details page lists each extension with its status, version, and ARN, and it’s where you install a new one. Each extension adds controls of its own, such as the metric store and an open dashboard in Grafana button for observability, and the number of customers and groups and a Manage users button for user management. You can also manage every extension through APIs, from the AWS CLI or an SDK, to script installs, keep settings in version control, repeat a setup across clusters, or check status and health from your own tooling. Industry observers note that when you create or enhancement an extension, HyperPod validates your settings against the version’s schema during the API call, so a misspelled setting is rejected immediately. It then records the version and settings as the desired state and applies them, with each node installing only what its role needs, such as GPU exporters on GPU nodes only. New and replacement nodes get the same state a few minutes after they start, and every node reports whether the extension applied and whether it’s healthy.

Sources indicate that updates send only the settings that you want to change, and HyperPod merges them into the stored settings. Problems that show up only on a node, such as a port or user ID that something else already uses, appear in the Health field of DescribeClusterExtension, grouped by cause with a code, a message, and a count of affected nodes. HyperPod retries internal failures on its own, and for anything else you fix the cause and call UpdateClusterExtension with no changes to retry the affected nodes.

Industry observers note that an extension’s status is Creating or Updating while a change rolls out, Active when every node runs the requested version and settings and none reports a problem, and Degraded when some nodes failed or report a problem. Each extension has its own ARN, so a platform team can own sagemaker-user-management while a monitoring team owns sagemaker-observability. Each health glitch names the component, describes the effect on your cluster, gives the next step, and counts the affected nodes, so you can see where to look without signing in to each node, as the following figure reveals.

A useful way to decide is to ask who owns the software and how often it changes. Some of the software on a cluster is specific to your organization, such as security agents, license servers, and the storage layout your data pipeline expects. Lifecycle scripts and custom AMIs are the right tools for it, because only your team knows what it needs. The rest is software that almost every cluster needs, like GPU and job metrics and user accounts with consistent IDs and access rules. That software must match on every node and keeps changing, so cluster extensions are the better fit, because you declare it once, HyperPod validates it, and each extension reports whether it’s healthy.

The two approaches can coexist, but each component should have one owner. Don’t manage the same exporter, user, or service through both a lifecycle script and an extension, because competing configurations can cause installation or runtime conflicts. Cluster extensions work with every lifecycle configuration option.

You need a HyperPod Slurm cluster on or after the November 2, 2026 HyperPod AMI or later with continuous provisioning enabled. An extension runs software as root on every node, so treat CreateClusterExtension, UpdateClusterExtension, and DeleteClusterExtension as administrator permissions. We suggest that you do not grant them to the cluster’s execution role, because every user who can sign in to the nodes can use its credentials. That role does need access to the destinations that the extensions use, which means Amazon CloudWatch or aps:RemoteWrite for observability and secretsmanager:GetSecretValue for the Active Directory secrets that user management reads. If those secrets are encrypted with a customer managed AWS Key Management Service (AWS KMS) key, the role also needs kms:Decrypt on that key. User management also needs a shared file system, such as Amazon FSx for Lustre, for home directories.

For procedures, IAM policies, and configuration references, see Cluster extensions for Amazon SageMaker HyperPod Slurm clusters in the Amazon SageMaker AI Developer Guide.

Recent findings suggest that to see how cluster extensions are used in practice, consider a platform team that manages a shared Slurm cluster for several research groups. The team needs a reviewable cluster definition, GPU and job metrics, corporate directory access, local accounts for a partner lab, and separate ownership of observability and user management. The following examples show how the team configures these capabilities and responds to routine changes and failures.

The administrator declares the whole cluster, including node roles, partitions, FSx mounts, minimum capacity, deep health checks, and the external accounting database, in a single CreateCluster request. For a complete example request, see Getting started with SageMaker HyperPod using the AWS CLI.

The request has no lifecycle configuration, topology file, or Slurm configuration file. Each SlurmConfig gives its instance group a role, and the GPU group joins the train partition. AMI-based configuration sets up the nodes, and the security team’s compliance agent is already in the custom AMI. The GPU group asks for 8 nodes and requires 6, so jobs can start as soon as 6 are ready while HyperPod provisions the rest and health checks each GPU node as it arrives. HyperPod selects tree topology for the P5 nodes on its own, and accounting writes to an Amazon Relational Database Service (Amazon RDS) database that the team owns. The administrator can still SSH into the controller node to inspect or tune Slurm directly.

Sources indicate that the user management extension manages the Linux users and groups on every node, and who can sign in and use sudo on each node type. You declare who should exist and what they can do, and HyperPod applies it to every node, including nodes added later or replaced, so no one connects to nodes or runs scripts to add or remove a user. Users come from local accounts that you list in the configuration, from Active Directory over LDAPS, or from both, and each group names the node types (controller, login, or compute) where its members can sign in over SSH and where they get passwordless sudo.

Recent findings suggest that for the platform team, security wants corporate identities, with sudo reserved for administrators, and a partner lab that isn’t in the directory needs accounts of its own. The administrator declares both sources in one configuration, with group rules that say which node types each group can sign in to and use sudo on:.

Access is explicit, so after the extension is installed only the groups that grant SSH access, along with the default ubuntu user, can sign in. Directory consumers keep their identities and group membership in Active Directory, while the partner lab’s users get the same IDs, home directories, and the default Slurm root account.

When AWS publishes a latest version of an extension, the administrator lists the versions that can be installed and upgrades in place without AMI updates:.

In a recent development, hyperPod checks the stored settings against the upcoming version’s schema and rejects the request, changing nothing, if they aren’t valid for it. Otherwise, the new version rolls out to every node, and nodes that join later get it too. Upgrades only go forward, so the administrator picks a maintenance window. Any new settings or capabilities that come with the version can then be turned on with an update like the earlier one.

Before the end-of-quarter run, the administrator starts an on-demand deep health check on the GPU group and then adds nodes with batch-add-cluster-nodes. The request returns as soon as HyperPod accepts it, so the administrator follows it as a cluster operation:.

As capacity arrives, each node is health checked, joins Slurm, takes its place in the topology, and gets both extensions with the same version and settings as every other node. If a GPU fails during the run, the replacement is configured and picks up the extensions the same way.

At the end of the quarter, security asks who has sudo on the controller, and the administrator answers from the API without signing in to a node:.

Recent findings suggest that the answer is cluster-admins and ClusterAdmin@example.com, and the directory group’s membership is audited in the directory. Because each extension has its own ARN, the platform team’s role can patch only sagemaker-user-management and the monitoring team’s role only sagemaker-observability, while security has read-only access to both. None of these permissions belongs on the cluster’s execution role. When an extension is Active, ActiveCount equals TotalCount, and Health is empty, every node runs exactly that configuration.

Cluster extensions, including the observability and user management extensions, have been available since November 2026 in all the regions where Amazon SageMaker HyperPod is supported, and the other improvements in this post were announced earlier in 2026, with each announcement listing its Regions. There’s no additional charge for cluster extensions. You pay for the AWS resources that you use with them, such as Amazon CloudWatch, Amazon Managed Service for Prometheus, and AWS Secrets Manager.

A cluster is easier to run when more of it is declared, validated, converged, and observable. This year’s improvements brought that to a HyperPod Slurm cluster’s definition, node setup, capacity, network topology, and hardware health, and cluster extensions, available since November 2026, bring it to the software on the nodes, the layer that changes most often. Lifecycle scripts and custom AMIs stay focused on what’s specific to your organization, and the controller node stays yours.
