📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Many teams that build applications self-host their identity provider (IdP), such as Keycloak or PingFederate, inside a private network. These IdPs usually present a TLS server certificate from a private certificate authority (CA). With private CA support in AgentCore Identity, a capability of Amazon Bedrock AgentCore, your agents can now connect to these IdPs while trusting the private CA that your organization already uses.

AgentCore Identity now supports private CA certificates for private identity providers. You store the PEM-encoded CA certificate in AWS Secrets Manager or Amazon Simple Storage Service (Amazon S3) and reference it from your credential provider. The CA certificate contains only the public certificate, not its private key. AgentCore Identity uses it to validate the server certificate presented by your IdP’s discovery, JSON Web Key Set (JWKS), and token endpoints. The CA certificate must be a root or intermediate CA certificate.

According to recent reports, in this post, we show you how to concern an IdP certificate with AWS Private Certificate Authority. We then configure an AgentCore Identity credential provider to trust it and rotate the CA while minimizing downtime. We also show how to protect the CA certificate so that only your IdP team can change it. Although AgentCore Identity supports any private CA, including enterprise, third-party, and self-signed root CAs, the walkthrough in this post uses AWS Private CA and Keycloak as the IdP.

It has been revealed that consider an agent that needs to call an internal wiki API protected by your Keycloak IdP. The agent runs on AgentCore Runtime, a capability of Amazon Bedrock AgentCore, which hosts your agent code. To get an OAuth 2.0 access token from Keycloak, the agent uses an AgentCore Identity credential provider, which holds the IdP connection details and client credentials.

The following diagram reveals this setup. Keycloak runs in your virtual private cloud (VPC) behind an internal Application Load Balancer. The load balancer presents an AWS Certificate Manager (ACM) private certificate signed by AWS Private CA. The CA certificate that AgentCore Identity trusts is stored in Secrets Manager or Amazon S3.

AgentCore Identity reaches the IdP privately through Amazon VPC Lattice, which connects to your VPC through a resource gateway, an entry point for VPC Lattice traffic into your VPC. VPC Lattice is required for private CA support. If you choose the managed option, AgentCore Identity creates and manages the VPC Lattice resources for you.

It has been revealed that after you verify that the credential provider trusts the private CA, monitor the CA certificate’s expiration and rotate it before it expires to prevent token request failures. AgentCore Identity publishes the EarliestCertificateDaysToExpiry metric to Amazon CloudWatch in the AWS/Bedrock-AgentCore namespace when your agents request tokens through a credential provider that uses a private CA. The metric reports the days remaining until the earliest certificate in your PEM file expires. It has ProviderName, ProviderArn, and TokenVault dimensions. When you create an alarm, specify all three. We recommend a CloudWatch alarm that notifies you well before the value reaches zero, because token requests to the IdP stop working when the CA certificate expires.

In a recent development, NOTE: AgentCore Identity reads the certificate only when you create or revision the credential provider. If you change the secret or S3 object, call UpdateOauth2CredentialProvider afterward so that AgentCore Identity reads the new content. Include certificateConfigurations in the update request. If you leave it out, the credential provider stops trusting your private CA.

A PEM file can contain more than one CA certificate and AgentCore Identity trusts each of them. You can use this to rotate to a new CA while minimizing downtime:.

AgentCore Identity doesn’t check certificate revocation lists (CRLs) or use the Online Certificate Status Protocol (OCSP). This means that if an unauthorized party obtains the private key for an IdP server certificate, AgentCore Identity continues to trust that certificate. This trust lasts until the certificate expires or until you stop trusting the CA that issued it. To stop trusting a CA, remove it from the PEM file and update the credential provider.

A CA certificate contains no private key and is public by design, because you hand it to every client that has to trust your IdP. What you need to protect is the data integrity of the trust store, meaning the secret or S3 object that holds the certificate. If someone replaces the certificate or adds another CA certificate to the trust store, the next revision could let an unauthorized party who can redirect traffic impersonate your IdP.

Sources indicate that we recommend that you scope permissions around writes rather than reads. Give write access, such as s3:PutObject or secretsmanager:PutSecretValue, only to the team or pipeline that operates the IdP. Give read access to the principals that call CreateOauth2CredentialProvider or UpdateOauth2CredentialProvider. During these operations, AgentCore Identity reads the CA certificate using the caller’s IAM permissions. Sources indicate that turn on S3 Versioning to recover an overwritten file and AWS CloudTrail data events to record each change. Because the CA certificate isn’t confidential, SSE-S3 encryption is sufficient and avoids the cross-account AWS KMS permissions that a customer managed key requires.

According to recent reports, keep the trust scope of each credential provider narrow. Upload only the CA that challenges your IdP’s server certificate, rather than your organization’s full trust bundle. If your IdPs use different CAs, store each CA certificate in its own secret or S3 object so that each credential provider trusts only the CA that it needs.

In a recent development, you can also use a private CA for inbound authorization.
