Across industries, decision-making starts with understanding what is changing and why. Industrial organizations collect data that informs decisions across their operations. This data helps prevent production stoppages, diagnose vehicle faults, explain drops in data-center performance, and adjust pricing as supply and demand shift. However, interpreting that data still requires specialist time, and collecting more data does not mean teams can act on it. General-purpose language models like Claude or ChatGPT can help analyze data. However, processing long histories across hundreds of operational metrics as text or images can consume large numbers of tokens, which increases cost.

To help organizations act on this data, Aionic Labs is developing temporal foundation models, including OpenTSLM, an open source family of time-series language models (TSLMs). These models interpret operational measurements, from equipment sensor data to supply and demand, alongside context such as maintenance records, market news, and an engineer’s observations. In doing so, TSLMs help systems recognize emerging problems in recent measurements. Experts can then ask follow-up questions to understand what changed and assess how to respond. TimeNet, the shared data infrastructure for time-series data, provides one format and API to find, build, and load the datasets used to train and evaluate these models. Together, they help organizations understand how their systems change and act before problems become costly.

Sources indicate that openTSLM is now available in Amazon SageMaker JumpStart, so you can deploy the model in your own AWS environment. This post explores how Nexthink and Aionic Labs are bringing this capability to proactive IT assistance, then reveals how to deploy OpenTSLM and adapt it to your own data using TimeNet.

The model in SageMaker JumpStart is OpenTSLM-Flamingo. It combines the Gemma 3 4B language model with a time-series encoder and cross-attention layers that let the language model attend to the encoded series. The model has 5.24 billion parameters in total, stored in bfloat16, so its weights take about 10.5 GB of GPU memory.

An application prepares numerical time series and text context, invokes the SageMaker endpoint, and receives the model’s response. The application can present that response to an expert or use it as input to another workflow.

This separation allows the application to control the observation window, select relevant signals, and validate the response before using it. It also makes the model independently adaptable: a new checkpoint can be evaluated against representative cases before the application switches to it.

For the deployment walkthrough, use an AWS account with an Amazon SageMaker AI domain and a SageMaker AI execution role. The role must be able to create SageMaker models and endpoints in a supported Region, for example a role with the AmazonSageMakerFullAccess managed policy. The quick setup for single owners creates both. The managed policy grants broad permissions to get started. For production, use a policy that grants only the permissions you need, as described in Amazon SageMaker AI identity-based policy examples. OpenTSLM runs on a single GPU with at least 24 GB of memory and bfloat16 support, and we recommend 32 GB of host memory. The default instance type is ml.g6.2xlarge (one NVIDIA L4 GPU with 24 GB of memory, 32 GB of host memory). In SageMaker JumpStart, OpenTSLM also supports ml.g6.4xlarge, ml.g6.8xlarge, ml.g5.2xlarge, ml.g5.4xlarge, ml.g5.8xlarge, ml.g6e.xlarge, and ml.g6e.2xlarge. In the Service Quotas console, check your quota for “ml.g6.2xlarge for endpoint usage”, or for the instance type you choose. You need a quota of at least 1. If it’s lower, request an increase. The endpoint accepts a JSON request with one or more instances. Each instance holds a question, one or more numerical series, and optional context lines. Each series has its values, a name, and a short description of the signal, such as its unit and sampling interval. A series can hold up to 32,768 values. The endpoint scales each series to a mean of 0 and a standard deviation of 1 and passes the original mean and standard deviation to the model as text, so the model receives both the shape and the scale of the signal. Use None for a missing value. The model masks it.

Send the request with the SageMaker Runtime InvokeEndpoint API. Set ENDPOINT_NAME to match your deployment. The calling identity needs the sagemaker:InvokeEndpoint permission. The following synthetic CPU example shows a request.

In a recent development, A request can hold up to four instances, each with 1 to 32 series, and the response contains one answer per instance in generated_text. max_new_tokens accepts values from 1 to 512. The model uses greedy decoding, so the same request typically returns the same answer. A real-time invocation must complete within 60 seconds, and the request body can be up to 6 MB. On ml.g6.2xlarge, the model generates about 20 tokens per second. The endpoint processes the instances of a request in sequence, so response time grows with the number of instances and the length of the answers: an answer of 512 tokens takes about 30 seconds. To stay within 60 seconds, send several instances in one request only with short answers, for example with max_new_tokens of 128. The 6 MB limit also bounds how much series data a request can carry. For long-running requests, you can use asynchronous inference.

Recent findings suggest that openTSLM-Flamingo compresses the encoded time series into a fixed-size set of representations before the language model uses it. This bounds the representation passed to the language model, but it does not make the complete system unlimited in memory or guarantee that a brief event remains easy to identify in a very long recording.

Industry observers note that long-context research makes this distinction concrete. TS-Haystack evaluates event retrieval across recordings of different lengths and finds that the evaluated TSLM variants often lose accuracy as the history grows, especially when locating event start and end times. These results motivate testing the chosen checkpoint on the windows and questions used by your application.

In a recent development, choose a window that contains the event and enough surrounding context to interpret it. For long recordings, compare overlapping windows. Preserve sampling resolution for brief events and align related channels in time. Include units, sampling interval, and the observation period in the text context. Validate both normal and abnormal examples at the intended lengths. The endpoint’s accepted payload size and the model’s useful analysis window are separate constraints.

According to recent reports, ARFBench is a public benchmark of multiple-choice questions about anomalies in Datadog’s software-incident telemetry. We use ARFBench because its multiple-choice answers can be scored automatically, which makes the effect of fine-tuning measurable. The same workflow applies to tasks with open-ended answers, such as the summaries and recommended actions in the Nexthink example. TimeNet serves ARFBench as a versioned dataset: each question is stored with its answer options, its correct answer, and the metric signals. The training job loads ARFBench through TimeNet and the model checkpoint from Hugging Face.

Industry observers note that A SageMaker training job runs the OpenTSLM training script on a GPU instance. The job fine-tunes the time-series encoder, the perceiver resampler, the cross-attention layers, and the language model’s token embeddings, and keeps the rest of the Gemma 3 language model frozen. The job saves the fine-tuned model to Amazon S3 in the layout of the Hugging Face model repository and writes the test accuracy before and after training to a metrics.json file. If your SageMaker Studio domain has a default MLflow App, the job also logs the training and validation loss and the test accuracy to it, so you can compare runs in the MLflow UI. In our run on one ml.g7e.2xlarge instance, accuracy on 135 held-out ARFBench questions rose from 5.0% to 45.9%. That is well above the 24.5% that random choice reaches on the full benchmark according to the ARFBench paper. Before fine-tuning, the model left most answers empty. Afterwards, it answered every question with one of the given options. ARFBench serves here as an example application: it indicates how to adapt the model to a newly introduced task and answer format with a public dataset. The result is not a comparison with other models or an official ARFBench leaderboard result.

Potential examples include interpreting equipment behavior with maintenance context, explaining energy-consumption patterns with operating conditions, and describing activity from wearable measurements. The data, supervision, and evaluation should reflect the domain and the decision the application is intended to support.

According to recent reports, preserve the timing and meaning of the measurements during preparation, and separate training and evaluation data in a way that reflects deployment. For a predictive task, only information available at prediction time belongs in the input. Domain experts should assess whether an answer is grounded in the signals and useful for the intended workflow. For free-text answers, compare them with reviewed reference answers, for example through expert ratings or LLM-as-a-judge, where a language model scores each answer against a rubric.
