📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that owners of a knowledge-grounded application expect it to remember them, not only to search well. They ask follow-up questions that make sense only in the context of the previous turn. They expect an answer about a policy or a procedure to reflect what they told the application about themselves last month. And they still expect every answer to be grounded in the documents they are allowed to read, with citations. Whether the application is a customer support assistant, a document chat inside a SaaS product, or an internal assistant over company policies, the expectation is the same.

Meeting that expectation is hard, because the context that would sharpen a search lives outside the knowledge base. A user’s location, role, or product tier was often mentioned in an unrelated conversation weeks ago. To use it, the application has to store every conversation, extract durable facts from it, decide which facts matter for the current question, and inject them into the request. When many customers share the application, every one of those steps also has to be isolated per user, and so does every document.

Amazon Bedrock Managed Knowledge Base and Amazon Bedrock AgentCore memory, a capability of Amazon Bedrock AgentCore, now take over these steps: storing each conversation, extracting facts from it, and bringing the relevant facts into the search. You turn this on by adding a memoryConfiguration to the AgenticRetrieveStream request, which makes AgentCore memory a retrieval source alongside your knowledge base. Within the same call, the service restores the conversation, and the planner decides on its own when a fact about the user would help. It retrieves that fact from long-term memory and uses it to compose the sub-queries it sends to the knowledge base. After generating the answer, the service saves the turn back to memory. The same request carries a userContext, so the knowledge base returns only the documents that the user’s access control lists (ACLs) allow. The integration is opt-in and backward compatible. Your application keeps only what is genuinely yours: authenticating the user and passing who they are.

This post shows how to build such an assistant for many people who share one knowledge base and one memory resource. Each user sees only the documents they may read, and each user’s memory stays private. The running example is an internal employee assistant for AnyCompany, a fictional company. Employees sign in with Amazon Cognito and ask questions over HR policies, IT guides, engineering runbooks, and sales looks. We show how to read the user’s identity from the Cognito ID token, how to pass it to AgenticRetrieveStream for document ACLs and for memory, how to design memory namespaces for many users, and how to read the trace to see when the planner used memory. Finally, we make AWS Identity and Access Management (IAM) enforce per-user memory isolation even when application code gets it wrong. If you deployed the application from Build multi-tenant agentic chat applications on enterprise data with Amazon Bedrock Managed Knowledge Base, this post replaces its “persist conversation history yourself” step.

AnyCompany keeps its documents in Amazon Simple Storage Service (Amazon S3). One managed knowledge base syncs them through an ACL-enabled Amazon S3 data source. A global ACL file in the same bucket says which employees may read each folder: everyone reads HR and IT, only engineers read the engineering runbooks, and only salespeople read the commission plan. One AgentCore memory resource is shared by every employee. Amazon Cognito authenticates employees, and its ID token supplies two claims: the sub (user ID) identifies the user’s memory, and the verified email identifies the user to the knowledge base’s ACL filter. Three test people sign in: two engineers, Maya and Liam, and one salesperson, Sofia. The trace excerpts in this post are taken from a run of the sample application in the GitHub repository.

Recent findings suggest that managed Knowledge Base owns ingestion, ACL filtering, indexing, ranking, planning, retrieval, and generation. With memoryConfiguration, it also owns session restore, memory search, and persistence. AgentCore memory owns storage, retention, encryption, and extraction. Your application owns authentication, the UI, and reading the user’s identity from the token. There is no conversation table: when the UI lists or reopens a conversation, it reads the same memory resource.

According to recent reports, every value is derived by the application from the verified ID token. None comes from the request body.

Two different claims do two different jobs. The knowledge base identifies consumers by email, because that is what the connected data source records in its ACLs. Memory needs an actorId that never changes and is never reused. The Cognito sub is both. An email address can be changed, or reassigned to a fresh employee after someone leaves, and that person would then inherit the old memory. You can use another stable user ID from your own user store as the actorId. What matters is that it never moves to a different person.

One memory resource serves every user. Per-user separation comes from {actorId} in the namespace templates, which AgentCore memory resolves from each event at extraction time. Two choices matter.

Strategies. The two strategies extract different things. The summary strategy summarizes each conversation, so it captures facts that a user mentions in passing, such as “I’m on a Mac in the Frankfurt office.” Those facts are what personalize a later answer about, say, PTO. The user-preference strategy extracts stated preferences into structured records (“Prefers short bullet-point answers without tables”, “Always deploys to eu-central-1 first”) and does not treat incidental mentions as preferences. Summaries give you “what we discussed.” Preferences give you “how this person wants to be answered.” Use both.

Layout. retrievalConfigs accepts one entry, so a single namespacePath must reach everything the planner should see for a user. Put {actorId} directly under the root: namespacePath: "/anycompany/" then covers the profile and every conversation summary. A layout such as /anycompany/profile/{actorId} and /anycompany/summaries/{actorId} would let one entry reach only one of them.

Recent findings suggest that you do not need your own table that maps consumers to sessions. Accepting a sessionId from the client is safe because short-term memory is keyed by (memoryId, actorId, sessionId), and the actorId comes from the token. The query before the call and the write after it are gone, and messages has one element. Three rules come with sessionBinding, and each is enforced with a specific ValidationException. Memory operations are best-effort by design. If a memory call fails or is denied, the request does not fail. The trace carries a FAILED memory event with the failure message, and the turn continues without that memory. The answer is generated from the knowledge base. Amazon Bedrock Managed Knowledge Base already gave you the retrieval stack as a service. That stack covers ingestion, document ACLs, indexing, ranking, and the planning loop in AgenticRetrieveStream that turns a hard question into a cited answer. With memoryConfiguration, the same call now carries the conversation and the user’s history. For a multi-user application, that removed the conversation store, the history replay, and the extraction pipeline. What remained was a short list of responsibilities. Authenticate the user and read two claims from the ID token: pass the verified email as userContext so that the knowledge base filters documents, and use the sub as the actorId for one memory resource with {actorId}-rooted namespaces. Use IAM condition keys on a per-user role session as a second line of defense that holds through the agentic path.
