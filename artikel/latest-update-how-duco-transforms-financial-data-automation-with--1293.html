It has been revealed that financial institutions face a critical challenge: processing massive volumes of data with speed, accuracy, and compliance while operating under some of the world’s strictest regulatory frameworks. Duco is the agentic Operations platform for financial services, serving tier-one banks and other financial institutions. It processes 20 billion transactions monthly for 200+ clients, including 7 of the top 20 banks and 10 of the top 20 asset managers. To keep pace as data processing demands grew, Duco evolved from traditional machine learning models to the agentic AI capabilities of Amazon Bedrock and Amazon Bedrock AgentCore. In this post, we share how Duco rebuilt its agentic AI stack on these services, cutting deployment time and onboarding costs while keeping each bank’s data isolated.

According to recent reports, duco’s platform empowers teams to automate mission-critical data processes using AI and no-code models, handling everything from data extraction to downstream publication. It already used traditional machine learning models for predictive labeling and pattern recognition, helping banks consolidate and automate over 20,000 processes.

However, these classical machine learning approaches had inherent limitations. They required extensive historical data for training, struggled with novel scenarios, and demanded significant customization for each new use case. Most critically, they couldn’t adapt rapidly to the diverse, constantly evolving data formats and business rules that characterize modern financial operations.

It has been revealed that “The classical prediction models worked to an extent, but they weren’t agile or flexible enough. Traditional machine learning models can only amplify what they’ve already learned — they can’t help with the next step or find new problems.”.

— Rob Gates, Chief Architect and Innovation Officer, Duco.

Duco made a strategic decision to adopt Amazon Bedrock for managed access to foundation models, and Amazon Bedrock AgentCore to run agents at scale. This was more than a technology upgrade. It was a fundamental shift in how its system could understand, reason about, and act on financial data.

Rather than committing to a single foundation model, Duco uses the right model for each job, assigning each role in its agent design to the model best suited to it. This approach delivers both quality and cost efficiency by matching the right model capability to each specific workload:.

This multi-model approach is architecturally designed to allow model swapping without disrupting the stack, which is critical in a landscape where model capabilities evolve rapidly.

One of Duco’s most significant technical innovations addresses a challenge familiar to anyone building production agent systems: context window management.

With 300–400 tools exposed per tenant through AgentCore Gateway (which fronts a separate MCP server for each underlying Duco service), approximately 200,000 tokens of tool descriptions were loaded into context before work began. This caused context overloading: response quality degraded as conversations lengthened, and the model lost the thread of earlier reasoning. The team emphasized that a feeling an agent is becoming less capable isn’t enough evidence on its own. Evaluations must be run before engineering decisions are made.

Duco created a skills architecture using MCP resource types to move tool descriptions out of the static context and load them only when needed:.

Three new meta-tools, implemented in Duco’s agent harness, replaced the bloated tool description payload:.

Figure 3: Context loading and MCP connectivity.

Sources indicate that A key architectural decision was implementing MCP tool discovery at boot time. When a newly introduced service is deployed, its MCP server is registered as a target on the tenant’s AgentCore Gateway as part of the deployment. When an agent boots, the harness builds a registry of every tool the Gateway exposes and shares just the tool names. The agent then uses find_tool and invoke_tool to discover the details and invoke tools on demand. As a result, the agent automatically gains that capability with no redeployment or agent reconfiguration required. Access control is enforced by the underlying services themselves: because the user’s identity is passed through the Gateway, each tool call succeeds only if that user is permitted to perform the action.

According to recent reports, this provides operational agility: the platform team can ship upcoming capabilities to agents by deploying a new microservice, without touching the agent configuration or requiring downtime. For a platform that serves 200+ clients with diverse and evolving operational needs, this dynamic capability model is a significant competitive advantage.
