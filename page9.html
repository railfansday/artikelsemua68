📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

During a traffic peak, a request can sit in a queue on a saturated HyperPod cluster while GPUs on another cluster, sometimes in another AWS Region, sit idle. You have already paid for that capacity, but your requests can’t reach it.

In Introducing Amazon SageMaker HyperPod Inference Gateway, we showed how the Inference Gateway gives each Amazon SageMaker HyperPod cluster a single, GPU-aware endpoint. It reads real-time signals such as key-value (KV) cache utilization and queue depth to place every request on the best-suited pod. That solves routing inside one cluster, but not across clusters.

Today, SageMaker HyperPod introduces the Global Inference Gateway. It is one SageMaker-managed gateway that routes across every cluster you register, in one Region or across Regions. The gateway picks the cluster and carries the request over the AWS backbone, with automatic failover and authentication through AWS Signature Version 4 (SigV4) and AWS Identity and Access Management (IAM). Inside each cluster, the Inference Gateway keeps picking the pod, unchanged. The Global Inference Gateway is the second tier of the architecture we described in part 1.

According to recent reports, models are getting larger, and the GPU capacity to serve them is harder to find. To get enough of it, you spread it across more clusters and more Regions.

Recent findings suggest that consider a team that serves four models across five HyperPod clusters in two Regions. Without the Inference Gateway, clients track 20 endpoints: one per model per cluster. The Inference Gateway cuts that to five, one per cluster. But each client still picks a cluster itself.

The team needs one endpoint that sends each request to the best-suited cluster and moves traffic off a failed cluster on its own.

The Global Inference Gateway helps you get more from the GPU capacity you already have, with less to operate.

Recent findings suggest that “At Bagelcode, we run our own LLM inference service on AWS to help teams across the firm, including our game teams, use AI to improve how they work. In our beta tests, the Global Inference Gateway in Amazon SageMaker HyperPod routed requests across two AWS Regions through a single endpoint and kept serving them when one cluster could no longer serve the model. That gave our small platform team cross-Region failover without having to build or maintain our own routing layer.”.

— Jinhyung Park, VP (AI Platform), Bagelcode.

Setting up the gateway takes two decisions: which clusters to open up for routing, and which of them to group behind one gateway.

A cluster is reachable only after you publish it. When you publish a cluster, the controller creates a Network Load Balancer in front of the cluster’s Inference Gateway, publishes a virtual private cloud (VPC) endpoint service on it, and uploads the listener’s certificate to your TLS bucket. These resources live in your account. If you list a cluster in a gateway before you publish it, the call fails with a message that tells you what to fix.

(2) The gateway authenticates the caller and picks the best cluster. (3) AWS PrivateLink carries the request to that cluster, in the same Region or another, and (4) the cluster’s Inference Gateway routes it to a model pod, as it does today.

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that frontier cloud LLMs carry high operational costs that can fluctuate unexpectedly, and relying on such third-party models introduces vulnerabilities, as providers can modify, deny, or deprecate access at any time. Furthermore, proprietary models offer limited customization for specific workflows, while posing risks to privacy, data control, and transparency. Besides, not every task demands frontier-level intelligence: small, specialized agents can be equally capable on specific tasks and significantly cheaper to run, since many routine or smaller workloads can be processed efficiently on-device. As intelligence per parameter continues to improve rapidly, we aim to stand at the forefront of this shift toward performant, privacy-focused, self-hosted models.

Tether AI Research introduces BotPsy, a 0.8B-parameter model introduce BotPsy, a 0.8B-parameter model designed for function calling and agentic workflows, built on top of Qwen3.5-0.8B and suitable for on-device deployment. BotPsy is a "personal assistant" that uses tools to perform a variety of simple tasks for the user, in domains such as web search & research, travel & lifestyle, commerce & finance, business & customer operations, device & vehicle control, files & documents, calendar, and email & messaging. Due to its small parameter count, it is best suited to tasks of low to medium difficulty. BotPsy achieves state-of-the-art (SOTA) tool-use and agentic performance for its size, outperforming every model of up to 1.2B parameters that we tested (Figures 1 and 2). Designed for secure on-device workflows, it provides exceptional instruction-following reliability and efficiency while keeping user data private. As a small model, BotPsy still makes mistakes and is not intended for high-stakes use; please read the Intended Use and Limitations for more information.

(“Tether AI Research”, “we”, “our”) will focus on expanding on-device agentic capabilities to seamlessly integrate with an even broader array of hardware and local services. Tether's Hypersearch will evolve to support more robust decentralized peer-to-peer (P2P) queries, further ensuring private, encrypted web searches that bypass corporate trackers. QVAC Fabric local fine-tuning mechanisms will be optimized to adapt more deeply to individual user preferences, workflows, and specialized tool environments. Future iterations will allow the smartphone interface to smoothly delegate heavy computational tasks to home PCs or trusted secure P2P nodes during offline-online transitions. Privacy protocols will be continuously strengthened to guarantee that all personal data, credentials, and decisions remain strictly on local hardware. Collaborative features will be introduced to allow secure agent-to-agent communication across trusted local networks without compromising user confidentiality. Ultimately, these advancements will solidify BotPsy as a fully autonomous, highly capable personal AI ecosystem that keeps customers entirely in control of their digital lives.

BotPsy is based on Qwen3.5-0.8B and is post-trained in four sequential stages: Supervised Fine-Tuning (SFT), Multi-teacher On-Policy Distillation (MOPD), and two rounds of Reinforcement Learning (RL). Each stage uses the previous stage's best checkpoint as its starting point and benefits from a different learning signal: imitation of reference trajectories, the token distributions of much larger teacher models, and rule-based tool-calling rewards (see Figure 3).

Our approach uses four stages of training, which learn from three types of signal: demonstrations, specialist teachers, and verifiable rewards.

Learning from demonstrations (SFT).

We first perform full-parameter supervised fine-tuning on tool-use conversations. These include multi-turn agent trajectories from simulated environments, replayed single, parallel and multi-step calls, and cases where no tool should be called.

Next, the student is trained with on-policy distillation (OPD): it generates its own responses, and a specialist teacher provides feedback on every token, using the per-token reverse KL divergence as the training signal. To build the teachers, we first RL-trained three Qwen3.5-4B models to specialize in tool use, general reasoning, and instruction following. During training, every prompt is routed to one of these teachers. This stage mainly aims to recover knowledge and instruction following, which degraded during the SFT stage, although the tool-use metrics also increase (see Figure 4).

Learning from rules and environments (RL stages).

Finally, the model is trained with reinforcement learning using DAPO [1], learning only from rewards computed by rules and verifiers. The first round focuses on tool calling, accompanied by instruction following and STEM multiple-choice questions. As in Tool-N1 [2], the tool-calling reward first checks the reasoning and tool-call format. Instead of Tool-N1's binary correctness reward, however, it gives fine-grained partial credit in the spirit of ToolRL [3], matching the predicted tool names, argument names, and argument values against the ground truth.

The second round widens the training mix to general-domain verifiable tasks: math, code, knowledge (multiple-choice) questions, instruction following, structured outputs, and multi-step tool use in a simulated workplace environment. Although this mix contains no multi-turn conversations, it further improves multi-turn function calling.

Each stage of training uses a different data mixture (Figure 5). The SFT stage focuses mainly on tool use and prepares the ground for the subsequent stages. The MOPD mixture combines tool-use, knowledge and instruction-following data, both to further improve function calling and to recover the general-domain regressions from the SFT stage. The first RL stage again focuses mainly on tool use, while the second RL stage shifts the balance toward general-domain data (instruction following, knowledge, math and code), keeping a smaller share of tool use.

BotPsy roughly doubles the tool-use performance of its Qwen3.5-0.8B base and is the strongest of the five models on five of the six agentic benchmarks: BFCL v4 (44.0 vs 23.4), ACEBench (58.7 vs 30.1), τ-bench (51.5 vs 23.2), BrowseComp-Plus (4.5 vs 1.9) and ToolSandbox (64.6 vs 30.5). On all five, it is also ahead of Qwen3.5-2B-Think, a model 2.5× its size (37.7, 55.4, 46.5, 2.8 and 41.2 respectively; see Table 1). On Claw-Eval, Qwen3.5-2B-Think leads (48.9 vs 46.5).

3D generation has many uses in robotics, simulation, media, and entertainment. In these fields, it is difficult to make generated objects obey strict rules and standardize model and data representations. There are many file formats, such as GLB and PLY. There are also many representations, such as neural radiance fields (NeRFs) and 3D Gaussian splatting (3DGS). Each one has different advantages and disadvantages.

TRELLIS introduced a common internal representation, called a unified latent representation. Its decoders convert this representation into 3D models in the required output format. Thus, you do not have to use different models for each representation format.

It has been revealed that the same team then released TRELLIS.2, which improves the model's representation of 3D structure. But neither model gives an easy way to adapt it to a specific task.

Recent findings suggest that A general-purpose model, such as TRELLIS.2, can make errors in details that are key for a specific application. For example, a user may need accurate geometry for furniture models. Without fine-tuning for that task, the pretrained model can produce geometry that is insufficiently accurate. We use a subset of GSO that has 188 footwear objects for our experiment. In our initial tests, the pretrained model usually produced shoes that looked correct, but the soles were incorrect. We test whether a LoRA can make the soles more accurate.

Recent findings suggest that our goal is to use the Google Scanned Objects (GSO) dataset to improve the performance of TRELLIS.2 on a specific object category. We will explain which pipeline components to fine-tune and which to leave unchanged during training. The pipeline separates structure, detailed geometry, and materials. Thus, we will fine-tune only the components that are crucial for our task.

Choosing what to freeze matters as much as choosing what to fine-tune.

In a recent development, loRA, short for low-rank adaptation, fine-tunes a model by training small adapter matrices while keeping the original weights frozen. This reduces the number of trainable parameters and the memory needed for their gradients and optimizer state. We use Hugging Face’s PEFT library to add and train these adapters. For more information, read our LoRA guide.

Before we train, let’s look at how TRELLIS.2 generates a 3D object and where we’ll add LoRA adapters.

TRELLIS.2 has five main stages: remove the image background, encode the image, predict the coarse structure, generate detailed geometry, and generate materials. The pipeline then exports the result as a textured mesh.

First, BiRefNet removes the background from the input image. DINOv3-L then encodes the image into feature tokens. The generation models use these tokens to guide the 3D object.

Industry observers note that the sparse-structure flow DiT predicts the object's coarse shape. It is a diffusion transformer (DiT) that makes a small latent of size 16³ × 8. A variational autoencoder (VAE) decoder then changes this latent into a 64 × 64 × 64 occupancy grid. Each voxel in the grid shows if that location is part of the object. A voxel is a pixel in three dimensions. We add LoRA adapters to this model because its output guides the geometry stage.

According to recent reports, O-Voxel is the 3D format of TRELLIS.2. It is a sparse voxel grid. It keeps only the voxels on the object's surface. Each voxel keeps local geometry, such as a mesh vertex, and material attributes. Because the format is small, a CPU changes a mesh into O-Voxel in seconds. A GPU changes O-Voxel back into a mesh in seconds.

Structured sparse latents come from TRELLIS. They keep 3D data in sparse tensors, which makes computation faster. The model uses only approximately 10% of the voxels in the grid, so it does not spend compute on empty voxels. Thus, the shape flow DiT and the texture flow DiT are sparse transformers. The sparse-structure flow DiT is a dense transformer.

Sources indicate that the shape flow DiT uses the occupancy grid and the DINOv3 feature tokens to make a latent. Another VAE decoder then changes this latent into O-Voxel geometry at a resolution of 512 × 512 × 512.

We add LoRA adapters to the DiT at this stage because it controls the object's shape.

According to recent reports, in the last stage, the texture flow DiT uses the shape latent and the DINOv3 features as input. It defines the materials and textures of the geometry's surface. A VAE decoder then changes the latent into base color, metallic, roughness, and alpha values for each voxel. We do not add LoRA adapters to this stage. Our dataset has diffuse color maps, but it lacks the separate material maps this stage needs for training. Also, our problem is the shoe's shape. The base model already makes good colors and textures.

Finally, the pipeline combines the geometry and material attributes into a textured mesh and exports it as a GLB file.

We add LoRA adapters only to the sparse-structure flow DiT and the shape flow DiT. These DiTs control the object's shape and geometry. We freeze the texture flow DiT to keep its current capabilities.

It has been revealed that our dataset contains diffuse color maps that include baked lighting effects. To train the texture flow DiT, we need separate material maps. The color maps in our dataset mix surface color with lighting. Thus, they are not correct targets for this training.

According to recent reports, if we train the texture flow DiT on these maps, it can learn to show lighting as a surface property. It can also forget what it learned before, a problem called catastrophic forgetting.

Industry observers note that our subset has 188 shoes from the 1,030 objects in GSO. For a dataset this small, LoRA is a better choice than full fine-tuning. Full fine-tuning costs much more. It can also overwrite what the model already does well (its learned priors). Our configuration trains approximately 9.3 million adapter parameters in total for both targeted DiTs. We use rank 8 adapters in the attention and feed-forward (MLP) layers of the sparse-structure flow DiT. We use rank 16 adapters in the attention layers of the shape flow DiT. The rank sets the size of the adapter matrices. A higher rank lets the adapter learn more.
